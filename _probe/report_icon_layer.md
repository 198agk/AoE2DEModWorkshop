# 图标层：十一次实机构建之后，能说的和不能说的

日期 2026-10-24。全部读数来自真开一局、真目视（截图放大 9–10 倍），
不是离线推断。城镇中心 109 血量 2400→4000 每次都作为「mod 到底挂上了没有」的
对照（面板读 4000 = 已挂载，2904 = 没挂载）。

## 一句话结论

**图标格（`icons.json` 的 `Units` 段）指向的材质名，只在游戏安装目录的
`materials.json` 里解析。mod 自带的那份 `materials.json`、以及
`morematerials.json`，都没有被读取。** 所以「给新单位/新科技配一张自己的图」
这条能力**写进去的字节是对的，但游戏不会画**——它画的是空框。

## 逐次读数（每一步只改一个变量）

| 版本 | 唯一的改动 | 屏幕上 | 这一版确定了什么 |
|---|---|---|---|
| v63 | `.dat` 里把出厂村民 83/1810 的 `icon_id` 改成新槽 1000，槽指我新加的材质 | 村民按钮**空框** | `.dat` 的 icon 字段确实驱动按钮 |
| v64 | 不动 `.dat`，只把 `Units["015"]`（村民）改成我的材质名 | **空框** | `icons.json` 被读；但那个名字解析不到 |
| v65 | 同上，但 DDS 抄出厂 128 字节头（payload 按 BGRA 写） | 斜纹 | —— |
| v66 | 同上，payload 按出厂头声明的 R/G/B/A 位置写 | **与 v65 逐像素相同** | 斜纹不是我的图；三次不同像素同一张画 ⇒ 那是「缺贴图」占位符 |
| v67 | 左半纯红 / 右半纯蓝 | **同一张斜纹** | 同上，且排除了「颜色被玩家色调制」 |
| v68 | 只改图集条目的 `FileName` 指向我的 DDS | 村民**正常** | 图集条目里的松散文件名不是那一格画的东西 |
| v69 | 槽指 `Type:"Texture"` 材质（完全照已发布三国 UI 模组的字段） | **空框** | Texture 材质在这条路上画不出来 |
| v70 | 自己新建一个 `Type:"Atlas"` 的图集（只装一张图 256×256） | **空框** | mod 新增的图集也不被采纳 |
| v71 | 槽指向**出厂已有**材质 `UnitIcons01650730` | 画出第 16 号单位的图标 | 名字确实被解析；出厂材质能画 |
| v72 | 材质放进 `morematerials.json`，并且**不带** `materials.json` | **空框** | `morematerials.json` 也没被读 |

v71 与 v64 是同一句话、同一处改动（`icons.json` 的一个字符串），
一个画出图、一个空框——差别只在那个材质名**在不在安装目录的表里**。
这是这一串实验里唯一没有被别的解释覆盖的一对。

## 为什么斜纹骗了我很久

按钮排上有三格：第 1 格（村民，出厂图标）、第 2 格（攻击/巡逻等命令）、
第 3 格（造斥候）。我在 v65–v67 里看的是**第 2 格**，那是出厂自带的图标，
和我的 mod 无关。三次不同 payload 画出同一张画本来就该让我先怀疑取样点，
而不是怀疑 DDS 编码。**教训：先证明「我看到的那个像素属于我改的那个东西」，
再讨论它为什么不对。**

## 已发布的三国 UI 模组说明了什么

- 它的 `icons.json` 把 `Units` 从 1000 扩到 2149 键，其中 **127 个指向它自己的
  材质**（`lt_soldier_unit_000` 等），`materials.json` 里也确实定义了它们
  （`Type:"Texture"` + `GlobalTextures`），DDS 是未压缩 256×256 BGRA。
- 它**没有** `morematerials.json`。
- 但它改了 **1149 个槽**，其中 1022 个是字面量 `"None"`。
- 按本轮读数，那 127 个「自己的材质」槽在我们的引擎里同样解析不到
  （v69 逐字段照它的写法做，仍是空框）。所以**要么它的自制图标在游戏里也是
  空框，要么还有一层我们没找到的入口**。这一点没有确认，是这条线唯一的开口。

## 产品上必须改的三处

1. `aoe2mod/game/iconart.py` 的 docstring 与 `aoe2mod/api.py` 两处 warning
   现在说「会把图作为新的一张图发出去」——**这是假话**，实测游戏不画。
2. `unit.create` / `tech.create` 的 `icon` 字段应当继续接受（字节写得对，
   等找到入口就能用），但预览必须明说「这一版游戏不会画出它」。
3. 钉子要钉住这个诚实边界，而不是钉住「三个文件都发了」。

## 还没试的（下一步，按成本排序）

1. **把材质名同时出现在安装目录的表里**：改的是安装目录 `materials.json`
   （需要备份 + 还原，风险中等，但能一次判定「是不是只读安装目录那一份」）。
2. 找那个三国模组的作者是不是还发了别的层（订阅文件夹里只有 `widgetui`）。
3. 反汇编/字符串搜索：`materials.json` 在 EXE 里命中 1 次，而 `icons.json`
   **0 次**——后者说明 `icons.json` 的名字是拼出来的或者根本没被引擎读，
   那 v71 的变化就要另找解释。**这条还没做，且可能推翻上面的结论。**

## 2026-10-24 追加：反汇编核对做完了，结论没被推翻，但被削窄了

原第 3 条（「`icons.json` 在 EXE 里 0 命中」，可能推翻结论）已经量完，**没有推翻**，
但把它的适用范围收窄了：

- EXE 里一共拼出 **44 个 `.json` 文件名**（`civTechTrees.json` / `linkedTechs.json` /
  `unitlines.json` / `objreplacement.json` / `materials.json` …），**其中没有 `icons.json`**。
- 但 `materials` 与 `morematerials` 在 EXE 里出现时**不带扩展名**，和其它 `.json` 名字
  排在同一张文件表里（`… paphosfutureavailableunits.json / morematerials / materials /
  unitcategories.json …`）⇒ 引擎对这两个名字是**拼出扩展名**的，所以
  「名字没有被拼出来」**不能**用来解释 `icons.json` 的缺席。
- 因此这条证据只支持一句：**`icons.json` 是另一条路径读的**，不能说明它没被读。
  而 v64/v71 那一对（同一文件、同一字符串、只差那个材质名存不存在于安装目录的表里）
  已经独立证明它**被读了**。

⇒ 一句话结论不变：**图标格的名字只对安装目录的材质表解析**。
收窄的部分：不要再用「EXE 里 0 命中」当作「这个文件不被读」的证据 —— 它只说明
`icons.json` 与 `materials.json` 不是同一张表里的兄弟。

另外两条实测（同一天，只读）：该三国模组的根目录只有 `info.json` + `thumbnail.png` +
`resources/` + `widgetui/`，**不带 `.dat`**，所以它改的全部是松散文件；它自己的
127 个 `lt_soldier_unit_*` 材质在我们复刻同一形状之后仍然是空框。

## 2026-10-24 追加：把材质写进安装目录，四次单一变量 + 一个必须先跑的对照

用户批准（`ask_user_question` → 「可以动游戏，做完还原」）后，把材质写进**游戏安装目录**的
`widgetui/materials.json`（先备份 2,494,306 B，测完逐字节还原、CRC 比对相同）。两个 `widgetui`
文件都不在 EXE 的 50 条 CRC 表里，所以不会触发「游戏文件损坏」。

| 做法 | 第一格画出来的是 |
|---|---|
| `Type: "Texture"` + `GlobalTextures` 指向我们自己的 DDS | 空框 |
| `Type: "Atlas"`，往出厂 `ingameunits` 图集的 `Textures` 添一条，UV 0/0/1/1 | 空框 |
| 同上，UV 改成「256/7168 × 256/7424」（按出厂条目的像素尺寸换算） | **杂色噪点** |
| 同上，UV 与 `FileName` 原样抄出厂村民那条（`0.535784,0.000067,0.571359,0.034415`，`textures/ingame/units/015_50730.dds`） | 空框 |

**这四次全部读不出来**，因为共享一个没验证过的前提：不带 `.dat` 的 mod（因此在数据模组下拉里根本
不出现）只留「默认」时，它的 `widgetui` 到底有没有被加载。补上对照后四次才有意义：

| 对照 | 第一格 |
|---|---|
| 同一份只带 `widgetui/icons.json` 的 mod，槽指向**出厂已有的** `UnitIcons01650730` | **画出 16 号单位的图（蓝衣女性）** |

⇒ 两个结论同时成立：

1. **只带 `widgetui` 的 mod 会被加载**（对照成立），所以上面四次的结果不是「没挂上」。
2. **往安装目录的材质/图集表里加条目，加出来的东西画不出来**：同样的 `FileName`、同样的 UV 矩形，
   换成出厂已有的材质名就画得出来，换成我们新加的名字就是空框。

也就是说：图标格做的是「**读名字 → 从已经烘焙好的图集里取那块像素**」，名字必须在
**烘焙那一刻就存在的表**里。出厂 `ingameunits` 图集 `Cached: "precached"`，图集 DDS 是
`textures/atlas/{SD,HD,UHD}/ingameunits.dds`（7168×7424）；794 条 256×256 条目已经占掉约 52.0 M
像素，图集总共 53.2 M —— **没有空位可以塞一张新图**。所以「新单位自己的图标」这条路，
在「往表里加条目」这个方向上不是没做完，是**引擎不会为后来加入的条目分配像素**。

尚未验证、也是下一步唯一值得做的：**mod 能不能整份替换那个烘焙好的图集 DDS**
（`textures/atlas/HD/ingameunits.dds`）。若能，新图标就有第二条路 —— 覆盖某个用不到的槽所在的那块
像素，再把我们的槽指过去。

## 2026-10-24 追加（二）：先补对照，再做一组「不改名字」的实验 —— 结论已闭合

### 必须先跑的对照（我一开始漏了）

前面四次「往安装目录加材质」都共享一个**没验证的前提**：不带 `.dat` 的 mod（因此不进数据模组
下拉）只留「默认」时，它的 `widgetui` 到底有没有被加载。若没有，四次结果全都无效。

| 对照 | 第一格画出来的是 |
|---|---|
| 同一份只带 `widgetui/icons.json` 的 mod，槽指向**出厂已有的** `UnitIcons01650730` | **16 号单位的图（蓝衣女性）** |

⇒ **只带 `widgetui` 的 mod 会被加载**。所以前面四次的空框不是「没挂上」，是真没画出来。

### 不改任何名字的实验（分离「表没被读」与「新条目没有像素」）

把已成槽值的那个**出厂**材质名 `UnitIcons01650730` 在 mod 的 `materials.json` 里改成
`Type: "Texture"` 指向我们的棋盘图；槽值不动（仍是这个名字）。

| 做法 | 第一格 |
|---|---|
| 出厂名 + 我们重定义 `MaterialDef` 指向棋盘 | **仍是 16 号单位原本的图** |

⇒ `MaterialDef` 里的 `Type`/`TextureRef`/`AtlasRef` **不参与绘制**。

### 闭合后的结论

图标格做的是：**拿槽值当名字，去一张烘焙期就固定的表里取那块像素**。

1. 槽值会被读（v64 换名字 → 画面变；对照换回出厂名 → 画面回来）。
2. 表里没有的名字 → 空框（v63/v64/v69/v70/w1/w3）。
3. 表里有、但被我们重定义 → **按烘焙时的定义画**（w6）。
4. 往安装目录加条目也一样画不出来（w1/w3），其中一个 UV 变体给出噪点（w2）。

所以「新单位带自己的图标」这条，**不是没做完，是引擎不会为后来加入的材质分配像素**。

### 唯一还没试过的路（留给下一轮）

**整份替换烘焙好的图集 DDS**：`widgetui/textures/atlas/HD/ingameunits.dds`（53,215,380 B，
BC7/DX10）与 `SD` / `UHD` 两份。若那条路可行，就变成「覆盖图集里某个用不到的槽所占的像素，再把
我们的槽指过去」。代价：要能解码并重编码 BC7 —— 当前 `aoe2mod/game/ddstex.py` 只支持
raw BGRA / DXT1 / DXT5 / DX10-BGRA，**不支持 BC7**，所以这条必须先加编解码器。
