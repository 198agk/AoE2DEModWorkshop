# AoE2 DE `.dat` game data

> **Starting cold, or resumed after a context reset? Read `项目状态.md` in the workspace root first** — it is the one-page cold-start entry (where the project is, the file map, the open questions ranked by value, and the exact commands that verify everything). This file is the operating manual for the `.dat` half.

The game data file is `resources/_common/dat/empires2_x2_p1.dat` — a **raw-deflate container** (`zlib`, `window_bits=-15`) holding a `VER x.y`-prefixed binary structure. The 4 MB `AoE2DE.dat` in the game root is a decoy: fully encrypted, no readable strings, entropy 7.999 b/B.

## Use the product kernel, do not rewrite it

**For anything that reads, edits or emits a `.dat`, start with `aoe2mod/` — it is the product, already wired and tested.** `_probe/` is the research notebook (and the source of the vendored engine); do not build on it directly.

```python
from aoe2mod import api
tk = api.open_toolkit()                      # finds the install; parses once, caches
tk.search("弓手")                            # candidates; NEVER raises
tk.describe(4)                               # name + hp/los/speed/attack/cost/train_time
tk.plan({"intent": "unit.stat", "unit": "Archer",
         "stat": "displayed_attack", "delta": 2})   # no bytes written; 126 edits, 63 of them mirrors
tk.build({...same...}, out_dir, author="me")  # -> installable mod folder
tk.plan_bundle([...several intents...])      # one request -> preview of ALL of them folded
tk.build_bundle([...], out_dir, author="me") # -> ONE mod carrying every sentence
tk.mods()                                    # real mods, engine Priority order
tk.install(out_dir, profile_root=...)        # -> copies into mods/local/ and registers it
```

**Product-level traps already paid for** — do not reintroduce them:
- **⚠⚠ NEW, DECISIVE: the `.dat` CANNOT express per-civilization unit availability — not "we have not found where", but "there is nowhere it could live".** Six independent refutations (`_probe/test_civ_unit_gate.py`, all assertions pass): **A** membership — unit 5 is present in the own array of all 63 civs, at the **same index**; **B** the record — with byte offsets stripped **recursively**, the 63 civs hold only **2** distinct records for unit 5 and the largest group (57 civs) differs in **0** fields (the one difference is `civ`, which is expected to differ everywhere); **C** the effect layer — the whole `.dat` contains only **7** type-2 disable commands and **none** names unit 5 (its single enable, `tech[85]`, is global, `civ = -1`); **D** transitivity — Chemistry (tech 47) is `ResearchedCompleted` for 62 civs and `None` for 1, so no prerequisite can produce a 38-civ block; **E** the `.dat`'s own TechTree — `DatFile.h` declares exactly one `genie::TechTree TechTree;` and `DatFile.cpp` serializes it **once**, so it is a **global singleton** and structurally incapable of a per-civ gate; **F** overlay depth — across the whole mod corpus exactly **one** file lives below `dat/` in a subdirectory, and it is **my own smoke mod that failed in game**; every third-party dat override is **flat** (`.dat`, `civilizations.json`, `linkedTechs.json`). **Consequence: the per-civ gate can only live in `CivTechTrees/<CIV>.json` — that is WHY it is a directory with one file per civilization.** So the open question stops being "where in the `.dat`" (that is now answered *negatively*, and re-searching it just reproduces the refutation) and becomes **"why does the overlay not take effect"**. **The cheapest explanation for THAT is already refuted too: "the overlay only reads the storage root, not subdirectories" is FALSE.** `_probe/test_overlay_depth.py` measures it: the `WIDGETUI` storage root holds **550 nested mod files, deepest 4 levels**, and the chibi emblem shipped at `widgetui/textures/ingame/emblems/lithuanians.png` (**depth 3**) is visible in the running game's command panel. So depth is not the reason; what remains is **load order** (is the tree read before mods are mounted?), **base-path-only reads**, or **the screen checked reading a different file** (`futuravailableunits.json` sits next to `TechTreePreviewPanel` in the exe string pool). **Lesson: "I have not found it" and "it is not there" are different conclusions, and only the second one changes architecture. And when an explanation happens to fit your single failing sample, look for a control case — the same mechanism with the OPPOSITE result — before believing it.**
- **⚠⚠ `.dat` DOES say who owns 46 of the unique units — in `UnitConnection.EnablingResearch`, a field `parser.py` reads and discards.** 266 unit connections; 47 point at a **civ-owned** tech (`tech.civ != -1`); for **46 of those 47** that owner is EXACTLY the one civilization the shipped tree says can build it (unit 8 Longbowman → tech 263 → civ 1 = British; 41 Huskarl → 270 → Goths; 725 Jaguar → 431 → Aztecs; 755 Tarkan → 1 → Huns). So **the earlier claim "the `.dat` cannot answer who can build what" is only about the per-civ `Node Status`**, which genuinely lives only in `CivTechTrees`. The dat gates **the owner**; the tree gates the **per-civ status**. **Do not repeat the blanket denial.** Caveat: this covers 46 of the 159 single-civ units, and it does NOT explain Hand Cannoneer (24 vs 38 — its enabling research 85 is global), War Galley (56 builders, no enabling research), or Knight (47/9, enabling 166 global) — **that split is still unlocated in the `.dat`** and is the biggest open question. `_probe/probe_enabling_gate.py`. **Lesson: before asserting "X cannot answer this", grep every `r.i32()` in the parser for X's structure and ask which one is read and thrown away.**
- **⚠⚠ A rewritten `CivTechTrees/<CIV>.json` DID NOT TAKE EFFECT IN GAME (2026-10-14).** The first real in-game test of `unit.availability` shipped ONE mod containing BOTH halves: a `.dat` villager HP edit (25 → 1000) and a rewritten `resources/_common/dat/CivTechTrees/BRITONS.json` (Barracks gains Champi Scout 2550 via `add_row`; Hand Cannoneer 5 flipped `NotAvailable` → `ResearchedCompleted` via `set_status`). The game log proves the mod loaded (`Enabling mod #0 (aoe2mod smoke villager HP + Britons units)`). User's verbatim verdict: **"村民血量 1000/1000，而且派活之后仍然是 1000。靶场里不能造 火枪手，兵营里不能造 蔷琵侦察兵。"** So: the `.dat` half worked (and the old TaskSwapGroup regression "派活之后恢复 25" is confirmed FIXED — it stays 1000 when reassigned), and the tree half did nothing in EITHER mode. **The tree file is a model, not a demonstrated lever** — it still agrees 99.45% with `futuravailableunits.json` (3261 agree / 18 disagree over the 55 civs that file covers), so keep using it for READING; but never tell a user an availability write will change the game, and never delete the `not_proven` sentence in `api._build_availability` that says so. See `_probe/probe_build_panel_gate.py`. Open: whether the engine ignores mod-side tree paths, or reads a different file/order, or needs `civilizations.json`'s `tech_tree_name` instead of the filename — **note that TWO explanations are already refuted and must not be revived: "the overlay does not recurse" (refuted by `_probe/test_overlay_depth.py`) and "the file name or FORM is wrong" (refuted by `_probe/test_tree_form.py`, below).**
- **⚠⚠ The tree file NAME and FORM are not the bug — the engine names exactly one template and it is the per-civ one.** `_probe/test_tree_form.py` settles it from shipped bytes with no game run. The exe contains `CivTechTrees/%s.json` **exactly once** (`0x3261a18`) and `civTechTrees.json` **exactly once** (`0x32e1678`, alone in its string run, **no path separator**). What makes the first one load-bearing is its **own generated field table ending immediately before it**: walking the NUL-separated string runs backwards from the template gives the row fields in **alphabetical order** — `Age ID` / `Building ID` / `Building in new column` / `Building upgraded from ID` / `Draw Node Type` / `Help String ID` / `Link ID` / `Link Node Type` / `Name String ID` / `Node ID` / `Node Status` / `Node Type` / `Picture Index` / `Prerequisite IDs` / `Prerequisite Types` / `Trigger Tech ID` / `Use Type` — then the file's three top-level keys in order `civ_id` -> `civ_techs_buildings` -> `civ_techs_units`, then the template as the cluster's last run; the enum clusters follow (`Draw Node Type`: `UnitTech`/`Age`/`Unit`/`UnitUpgrade`/`Research`/`BuildingTech`/`BuildingNonTech`/`UniqueResearch`/`UniqueBuilding`/`UniqueTech`/`RegionalUnit`/`RegionalBuilding`/`RegionalTech`/`BuildingExtra`/`Tech`, then `Node Status`: `Available`/`NotAvailable`/`ResearchedCompleted`/`ResearchRequired`), in the order the schema declares them. **`Name` is the one row key that is NOT its own run there (17 of 18) — the linker pooled it (only 2 bare `\x00Name\x00` runs exist in a 72 MB image). Count the runs you expect from the STRING POOL, not from the JSON key list, or this assertion fails while nothing is wrong.** The aggregate is a **MODE-only artifact**: the base game ships 62 per-civ files and **zero** aggregates; the only one on the install is `modes/Pompeii/resources/_common/dat/civTechTrees.json` (1,671,526 B, covering the 17 Rome civs) — and `DAT` is the **only one of the 28 declared storage points** carrying `use_modes_path_for_mods: True`. The two forms are **semantically identical**: over the 17 shared civs, 2,142 rows appear in both, **shared-key VALUE differences 0**, both unions are exactly the same 18 keys, and the aggregate merely spells out default-valued keys the per-civ files omit (2125 rows where the aggregate row is a strict key superset — **0** the other way). **Consequence: `unit.availability` writes the right file in the right form; stop looking for a naming bug and look at scheduling or at WHICH SCREEN the user checked.**
- **⚠⚠ "The game wants the .dat, not the JSON" is TRUE about a data mod replacing the .dat, and FALSE as a general rule that "JSON is not game data".** Never generalise it — doing so writes off the whole `*.availability` product line. `_probe/test_json_is_engine_data.py` (permanent, exit=0) refutes the general rule from the game's own behaviour, in three steps: **(1)** per-civ unit availability is *enforced by the running game* (the user saw it: as Britons the Archery Range offers no Hand Cannoneer, while 24 civs demonstrably build it); **(2)** the `.dat` **cannot** carry that distinction (see the six refutations above — unit 5 sits at the **same array index** in all 63 civs, its record is identical but for decorative fields, its only type-2 command is **global**, and the `.dat` TechTree is a global singleton); **(3)** **both** JSON layers *do* carry it per civilization — `CivTechTrees` gives Turks `ResearchRequired` vs Britons `NotAvailable`, and the build panel lists unit 5 for Turks' Archery Range (87) and **not** for Britons'. → **at least one JSON layer is engine input.** So the 2026-10-14 tree rewrite failing is an **OVERLAY problem on one path**, not proof that JSON is ignored. Keep the two apart: the first is a bug to chase, the second would condemn the feature. **NOT PROVEN**: which of the two layers the build panel consults (the 18 shipped disagreements need **no mod at all** to observe — that is the cheapest way to settle it), and whether dat-layer JSON **overrides** work (the corpus still has no positive example). **Lessons: (a)** when a `load_all()`-style helper returns `{key: {"text","obj","path"}}`, the `obj` is the **whole multi-civ document** — the subtree is `obj[key]`; getting this wrong returns `None` for every lookup, and **a `None` reads like a fact about the game while being a fact about your function**, so guard it (`if any(v is None …): raise SystemExit("… a fact about this probe, not about the game")`) — it passed my printed verdict twice. **(b)** Before promoting a specific correct statement into a general rule, look for one counterexample; here the counterexample was cheap and the rule would have cost a product line.
- **⚠⚠ NEVER assume the `Enabled` flag you wrote is still there — the game rewrites `mod-status.json` and may switch your mod OFF.** After the smoke tests, the rewritten file had ALL EIGHT mods that carry a `resources/_common/dat/` override at `Enabled: false` (3 of mine + 5 third-party data mods), while all FIVE enabled mods had no dat-layer override at all. Whether the cause is "data mods get disabled" or "mods that conflict with the enabled set get disabled" is **not distinguishable from this observation** (the two explanations are perfectly collinear here: every enabled mod was a texture/text/AI mod). Product rules: **re-read `mod_status` after the game has run, never trust your own write; confirm `Enabled` is true before reporting an in-game result** — otherwise a "no effect" observation may only mean "not enabled". This is why the first smoke test (villager HP 1000) DID show an effect: that mod was enabled at the time.
- **⚠ The cheapest availability experiment needs NO mod at all.** The game ships two files that disagree on 18 real (civ, unit) pairs (`_probe/probe_shipped_disagreement.py`): the panel file (`resources/_common/dat/futuravailableunits.json`) omits 7 units the tree calls trainable (Goths Huskarl, Huns Tarkan — gated behind a unique tech) and lists 11 the tree calls `NotAvailable` (Jurchens Long Swordsman line, Muisca Halberdier, ...). **The panel file has no place to express "gated behind a research", so it is not a per-civ availability model the way the tree is.** A normal game, no mod, answers which one the engine obeys. Two joins are load-bearing and both were gotten wrong first: the panel keys civs by DISPLAY name (`Britons`) while trees key by FILE stem (`BRITONS`), so go through `CT.civ_file_stem()`; and the panel also lists BUILDINGS under building `118` (`Builder`), so scope the comparison to the 287 ids the tree actually models as units.
- **⚠⚠ Not every JSON under `resources/_common/dat/` is a cache of the `.dat`, and the corpus cannot prove ANY of them override in game.** `_probe/test_dat_json_override.py`: of the 8 mods in this profile that touch the DAT storage root, **every one that ships such JSON also ships the `.dat` that explains any observed effect** (the only JSON-only mod is our own smoke test, whose single in-game run never started). So a positive result for `unit.availability`/`tech.availability` needs a new experiment, not a new reading. **But `linkedTechs.json` is real data**: `_probe/test_linkedtechs_semantics.py` shows its 20 `NameId`s all resolve to display names, its `MutuallyExclusive` (16/16) and `Toggleable` (13/13) groups ARE mutual in the `.dat`'s type-102 layer, and its **`Cycle` groups (12/12) are NOT** — the `.dat` can say "these two exclude each other" but cannot say "these three are one named cycle", so the file is not a cache. **Slot trap paid for here: a type-102 row puts the disabled tech id in slot D as a FLOAT** (`a=-1 b=-1 c=-1 d=1196.0`); reading `row["a"]` finds nothing and "proves" the two files are unrelated.
- **⚠ A build must never write into the GAME INSTALL, and there is a probe that proves it did not.** After the smoke tests above, a later session popped `试图开始游戏时发生一个错误。无法打开文件： .gpv` (note the EMPTY file name). That message is a **campaign** failure and has nothing to do with `.dat` work: `.gpv` files are packed campaign packages named `<campaign>.aoe2campaign.gpv`, tagged with the DLC name REVERSED (`cam1` → `esaB` = "Base", `3kcam1` → `ureP` = "Peru", `cscam1` → `1paP`, `ccam1` → `4CLD`), and **42 campaigns ship but only 17 `.gpv`**; no text file anywhere in the game tree or the mod folders names one, and the popup's wording comes from `IDS_FAILED_TO_OPEN_FILE` in `key-value-strings-utf8.txt` (it is not an exe literal). `_probe/probe_install_safety.py` pins the invariant that matters: the game's own `futuravailableunits.json` still does NOT give Britons Champi Scout at the Barracks nor Hand Cannoneer at the Range (both edits exist ONLY in the mod copies), the game's `CivTechTrees/BRITONS.json` still bans both, every path in `mod-status.json` resolves outside the game root, and no installed mod ships campaign content. **A `'"ID": 2550' in gametext` check is WRONG** — Champi Scout really is in the game file for Incas/Mapuche/Muisca/Tupi, so parse the JSON and look at the civ key. NOT PROVEN: what emptied the campaign name; the popup is UI-level and appears in no log (the session's log ends with a clean `Exiting with code 0`).
- **The `.dat` on disk is deflate-compressed and a mod's copy must be too.** Writing the raw stream yields `game inflate path: already-decompressed`. Use `emitter.deflate_raw(raw, level=6)` → `zlib.compressobj(6, zlib.DEFLATED, -15)`.
- **Never hash-compare an emitted `.dat` against the base file** — one is compressed, one is raw, so it never matches and the redundancy check silently never fires. Inflate the base first and compare **raw streams**.
- **`api.py` is at the package root: use `from .dat import ...`, not `from ..dat import ...`** (`ImportError: attempted relative import beyond top-level package`).
- **`warm(stats, game_root)` — always pass `game_root`.** The fourth family mechanism reads `objreplacement.json`, which lives under the install; `stats` carries **no path key at all**, so omitting it silently returns the older families (villagers fall from 27 records to 14) with no error. The list of callers that must pass it: `api._families()`, `compiler.compile_edits` / `compiler.unit_targets`, and every probe that builds families.
- **`game_root_of_dat()` strips FOUR path components, not three.** `<root>/resources/_common/dat/<file>` is the filename plus three directories. Stripping three leaves `<root>/resources`, which fails validation and returns `None` — that silently dropped the declared swaps on the one code path that derived the root from the `.dat` (callers passing only `parsed=`/`stats=`) and produced a **`plan()` saying 1701 edits while `build()` wrote 882**, with all four suites green.
- **A marker list containing only the `.dat` is a CIRCULAR validation.** `game_root_of_dat` derives a candidate root *from* a `.dat` path and then "proves" it by looking for that same `.dat`, so any directory shaped like an install passes — copying the `.dat` into `%TEMP%\notagame\resources\_common\dat\` was accepted as an install. `_GAME_MARKERS` therefore requires **both** the `.dat` **and** `AoE2DE_s.exe`; the executable is the marker a bare copy of the data file cannot fake.
- **Never render a float amount with `%d`** (`-0.1` displays as `+0`). `describe()` uses `%+.3g` for floats.
- **★★★ Which machinery compiles an intent is the SCHEMA's decision, not a name check in `build()`.** `unit.availability` is the first intent whose product is not a `.dat`: it writes `resources/_common/dat/CivTechTrees/<CIV>.json`, and the `.dat` cannot express it at all (see the `Enabled`/`Disabled` trap above). `build()` therefore dispatches on `spec["compile"]["strategy"]` and `compile_edits()` refuses any strategy that is not `in_place_patch`. **Assert the routing in BOTH directions** — "no `.dat` was written" also holds when the router is broken, because `compile_edits` refusing produces the same observable outcome.
- **★★★ A build must never edit the tool's picture of the game.** The `.dat` path patches an immutable `bytes`, so `plan → build → plan` answers identically. The JSON path edits a mutable dict held in `_trees()`'s cache, so a build that mutates in place makes the tool afterwards say *"it already has it, nothing would change"* — a silent lie about the game, and one a `describe()`-driven UI cannot detect. Build on a **full JSON round-trip copy** (a shallow copy shares the row dicts, and `set_status` edits a row in place), and keep **every** civilization in the proposal dict because `grant` finds its donor row by searching the corpus — handing it one civ raises `ValueError: cannot grant node 41 without a source row`. The permanent assertion is that planning the same sentence after a build returns the **identical** answer.

- **A sweep is only as wide as the options it exercises.** `_probe/test_full_sweep.py` iterates the schema's *declared* option lists (`unit.stat` × 14, `unit.cost` × 5, `unit.attack_class` × 2, tech × 2, `tech.effect`) instead of a hard-coded sample, and asserts every declared shape was planned **and** built at least once — otherwise a newly declared option would "pass" by never being tested, which is exactly how `max_range`/`reload_time` stayed unbound.
- **★ A "every declared thing is covered" guard only proves the things it ENUMERATES are covered.** `tech.effect` sat declared in the schema and unexercised for a whole round: the sweep's case list was hand-maintained and simply had no `tech.effect` branch, so the coverage guard printed `NEVER EXERCISED none` while covering five of six intents. Derive the enumeration from the schema (`sorted(intents_schema["intents"])` + a prefix match against the exercised keys), never from a list a human keeps in sync. **The whole `tech.effect` write path — the only one whose bytes land in a SHARED record — had no cross-boundary sweeper at all**, only a handful of hand-written cases; `_probe/sweep_tech_effect.py` now covers every (tech, command) pair: 8,005 commands, 6,599 editable, `agreed 13108 / refused by both 2902 / mismatches 0`, `0 collisions` on write offsets, `0` edits landing outside the Effects array, `fan_in` measured against the true sharing count on all 1,510 techs (203 share), `checked 6518 edits, 0 ineffective`, and 4,384 packed-byte range edges exact.
- **★ A whole command FAMILY can be refused by one missing table.** `_EFFECT_OPERATION` listed only the 21 attribute-modifier types (set/add/multiply × 7 scopes), so effect command types 1 and 6 — `Resource Modifier (Set/+/-)` and `(Multiply)`, **236 + 117 commands over BASE** — fell to the `else` branch and were reported read-only. The refusal wording was correct (they do carry no attribute) but the consequence was that 142 techs had **no editable command at all**, including every civilization's starting-resource grant. Resource rows cannot live in `_EFFECT_OPERATION`: **one type carries two operations** (slot B: 0 = set, 1 = add), which a single `(operation, scope)` pair cannot express. They need `_RESOURCE_SCOPE` / `_RESOURCE_CHANGE` / `_RESOURCE_MULTIPLY` and an operation read from slot B.
- **★ On a resource modifier, slot C is a TIMES-RESOURCE, not an attribute.** `attribute` therefore means a *resource id* on those rows, and the id spaces overlap: a slot C of 8 or 9 would be read as the packed armour/attack byte and the number decoded as a garbage pair. The `resource` flag on the row is what prevents it, and the write path must store `float(after)` rather than `encode_effect_value(cc, ...)`. Two shapes stay **refused with a reason**: `C != -1` (17 commands scale by another resource's *current value*, so "add 175" is not the edit it looks like) and a slot B outside `{0,1}` (8 commands).
- **★ A civ's opening bank is reachable ONLY through the effect path.** The per-civ `Resources` array (`parser.py:861`) is **all zeroes** at indices 91-94 (`Starting Food/Wood/Stone/Gold`) across all 63 civs — writing it changes nothing. Starting resources are `Resource Modifier` commands on each civ's free C-Bonus tech (tech 223 Persians +50 food/+50 wood, 224 Aztecs +50 gold, 225 Huns −100 wood, 226 Chinese −200 food/−50 wood, 227 Mayans −50 food, 228 Sicilians +100 stone, 1394 Tupi +25 each, 12 commands total). Those techs carry the genieutils placeholder `LanguageDLLName 7000`, so their display name falls back to a self-describing internal name (`C-Bonus, +50f +50w`).
- **★ A resource row's preview sentence has to describe the OPERATION.** A `multiply` row's number is a factor, so `+0.05` must render as `×1.15`, not as adding half a unit of something; a `set` row renders as `设为 4` rather than a cryptic `=4` next to a resource name. Delta on a multiply row means `old + amount` on the *factor itself* — never a relative change, because a preview must let the user check the arithmetic. Gate the sentence rewrite on `attribute_label or target_kind == "resource"`, not on `attribute_label` alone, or resource rows get described as the bare tech name.

- **★ When a new sweeper reports failures, suspect the assertions' SHAPE before the product.** Two rounds of "defects" in `sweep_tech_effect.py` were both mine: (a) comparing a float32 field against a Python (binary64) float reports `2.4` as unequal to itself — round both through binary32 first; (b) asserting "`+255` is always refused" tests arithmetic, not the guard — the rule is the **range** `0..255`, so `+255` is legal from 0 and illegal from 1. Never hardcode a delta; compute `room = 255 - before` and assert `room` accepted / `room + 1` refused, **and** `-before` accepted / `-(before + 1)` refused — a one-sided `<= 255` passes an upper-edge-only test while having no lower bound at all.

- **★ An enum is a promise about the data; an unchecked promise is a list somebody once typed.** `intents.json` declares `unit.cost` over 5 resources and `tech.cost` over 4 — a real asymmetry, since no shipped tech charges population. Nothing asserted it until `_probe/test_declared_resources.py`, which walks every cost slot of every unit and tech record in the shipped `.dat` and requires the charged set to be **exactly** the declared option set. A game update that makes a tech charge population, or a unit charge something the schema forgot, now fails there instead of leaving that intent silently unable to reach the new slot. Same file also asserts the unmapped side is honest: every non-declared type is either named by the game's own table or **absent** (never present-but-empty, which would read as "named, name is empty").
- **★ "It was refused" hides two opposite repairs — always split the count.** `_probe/probe_refusal_reasons.py` separated 1,745 refusals of `tech.effect` into **1,585 = "command type not in the operation table"** (a missing FEATURE, needs code) and **160 = "attribute id has no name"** (a missing LABEL, needs a data file only). Reading them as one number makes it look like all 1,745 need a parser. The 160 rows were perfectly well-shaped attribute modifiers whose only problem was that nobody knew what attribute 81/118/119/125/126/127/130/145/146/147/158 was called. **Refusing to invent a name is right; refusing to ship a name the game already has is just a missing file.**
- **★ The game ships its own attribute-name table: string id = `12200 + attribute_id`.** `_probe/probe_attr_name_blocks.py` enumerated every candidate base 0..59,999 and found exactly one satisfying four undisputed anchors (0 `Hit Points`, 1 `Line of Sight`, 2 `Garrison Capacity`, 5 `Movement Speed`). The block spans `12200..12461`, 242 named slots, 20 real holes, and names **all 11 ids AGE can't** (`81 Special Ability`, `119 Friendly Fire Damage`, `130 Garrison Firepower`, `145 Trailing Unit`, `158 Train Locations Entry Mod`…). Generator: `_probe/schema/build_attribute_labels.py`. **Do not confuse this with the runtime ids `42020='Selected Object'`/`42024='Attacks'`** — different id space, not this table.
- **★ Supplement, never replace — and price the replacement before making it.** AGE's 89 names differ from the game's wording on **66** ids, **54** of which sit on live shipped commands covering **5,194 of 6,420** attribute-modifier rows, almost all of it AGE annotating its own UI (`Movement Speed (types 20-80)` vs `Movement Speed`). Adopting the game's wording wholesale would therefore reword 5,194 labels under the banner of fixing 160. `_attribute_label()` returns AGE's name whenever it exists and only consults the new table when it doesn't, so **no existing label moves**; whether to adopt the game's phrasing everywhere remains an open, measured decision. Verify with `_probe/probe_attribute_unlock.py`: `rows STILL refused for a missing attribute name: 0`, `ids where AGE's name was overridden: 0`, and the game-words-it-differently count still 1,884.
- **★ Before copying a neighbouring generator's guard, ask why it exists.** `build_resource_labels.py` asserts the block is a contiguous 551 slots — true for `15000..15550`, which has no holes. The attribute block has **20 real holes**, and the copied guard fired as `FATAL: English block covers 242 of 262 slots; the 12200+attribute_id scheme does not hold`. The guard was not just wrong, it was **weak**: a shifted base counts 242 just as happily. What actually proves a base is the **anchors**. Also: `drop_unused` must key off the **English** wording only — filtering the Chinese file with English words matches nothing and silently ships 224 "names".
- **★ A refused row has no label by construction, so comparing its label always "disagrees".** `effect_rows` assigns `attribute_label` under `if pair:` (the operation-table lookup), so `probe_attribute_unlock.py` reported 317 phantom "AGE name overridden" rows and 339 phantom "editable with no label" rows — the first because it compared refused rows, the second because it counted resource-modifier rows (whose slot C is a times-resource, so a `None` label there is correct). Filter on `r["editable"]` and on the attribute families (`operation in ("set","add","multiply")` and `target_kind in ("unit","class")`). **Fourth time this project's probe assertion, not the product, was the defect.**
- **★ A dict's already-computed field beats a string you hand-concatenate 100 lines later — that gap is why raw ids leak five times.** `effect_rows` built `type_label` (localized) in the row literal at `compiler.py:496`, then refused with `"command type %s does not carry an attribute" % t` at `:583`, i.e. it printed the number while the name sat in the same dict. Now `% row["type_label"]`, which still falls back to `Type %d` so an unnameable command is never given an invented name. This is the fifth member of one family: `cost type 3` → cost labels; `attack cls 4` / `armour cls 3` → class labels; `location[0]` / `train[2]` → location labels; `unit.stat` previews → unit-field labels; and now command types. **Before emitting any user-visible sentence, ask whether every variable in it is already in a human's language.** Assert it over the whole population with a **two-condition** test (`re.search(r"type\s*\d", why)` OR the row's own `type_label` equals its `Type %d` fallback), never a single regex — and print the count scanned, so a loop that scans nothing can't pass.
- **★ Fixing a defect invalidates every check that PRESUMED the defect.** After the 160 unnamed-attribute commands were unlocked, `probe_refusal_reasons.py` kept printing `type 0/4/5 refusals are all 'attribute has no name': False` — a stale assertion whose text encoded the pre-fix condition. Sweep the probes for their negative-summary lines whenever a refusal count changes, or they read as permanent false alarms.
- **★★★ A field whose NAME promises the feature is not evidence — and the `.dat` does NOT decide which civs can build what.** `parser.read_unit()` reads two u8s genieutils calls `Enabled`/`Disabled` right after `OldPortraitPict`; they are **not** an unlock switch. Measured: only **7 of 2,693** ids carry a differing value across civs, and between British and Goths **0 of 2,164** shared ids differ in those bytes while the game's own data gives British 24 ids Goths cannot have and Goths 14 British cannot. **0 versus 24 kills the hypothesis outright.** The `.dat` TechTree section cannot do it either — `parser.read_tech_tree` is called ONCE, a single global table. **Never promise "flip a flag to unlock unit X for civ Y".**
- **★★★ "Has it" and "can build it" are DIFFERENT predicates, and this layer conflated them once.** `ResearchedCompleted` = has it now; `ResearchRequired` = **reachable by research, so the civ CAN build it**; `NotAvailable` = listed in the UI and never obtainable; no row = not in that civ's tree. So **"can build" is `ResearchedCompleted` OR `ResearchRequired`**, and only `NotAvailable` / an absent row is "cannot". The decisive case: **War Galley (21) reads `ResearchRequired` for all 56 dock-owning civs** — a reader requiring `ResearchedCompleted` reports that NOBODY in the game can build a War Galley. Use `can_build(tree, node_id)` for the ability question and `has()` only for "right now"; `builders(trees, node_id)` is the list `owners()` was mistaken for (they differ on 14 of 287 nodes; `owners=0` nodes went 10 → 0). This also fixes **`donor_row`**: picking the first row in sorted order copied, on **12 nodes**, from a civ whose own row reads `NotAvailable` (Hand Cannoneer came from ACHAEMENIDS when ATHENIANS has a real one) — and on **5 of those the two rows differ in exactly the inherited fields** (`Name String ID`/`Picture Index`/`Help String ID`, plus `Age ID`/`Link ID`/`Trigger Tech ID` on node 567), so the granted unit would train at the wrong age with the donor's icon. It now prefers a civ that already has the unit over one still working toward it.
- **★★★ Absent ≠ unobtainable, and the two need different sentences.** A `NotAvailable` row must be reported as "listed but not obtainable" (a status change fixes it) and never as "absent" (a row must be added). The read side mirrors this: `describe(unit)["availability"]` returns `holders` / `builders` / `absent_from` / `blocked_in` (NotAvailable) / `pending_in` (ResearchRequired), and is **`None`** — not empty lists — for a record that is in no tech tree at all. **Buildings ship as unit records** (id 12 = Barracks), and an empty list there would read as "nobody can build it". Also: `describe()`'s `civ_count` is the **`.dat` record count** (always 63) and answers a different question from `builders`; the two disagree on **287 of 287** nodes.
- **★★★ Per-civ availability lives in `resources/_common/dat/CivTechTrees/<CIV>.json`, and `Node ID` is NOT one namespace.** Use `aoe2mod/game/civtechtrees.py` (read AND write): `load_trees`, `unit_rows`, `node_status`, `has`, `can_build`, `builders`, `owners`, `name_string_id`, `collide_with_tech_space`. Three facts it encodes — (a) **absent means absent**: a civ that cannot obtain something has NO row, not a falsy status, so `has()` is `row is not None`; (b) the row's `Name` field is **stale on 44 rows** (all Chronicles) — display `Name String ID`; (c) the three status words mean three different things to a player — `ResearchedCompleted` = has it now, `ResearchRequired` = **can build it once researched** (so it IS buildable), `NotAvailable` = listed and never obtainable — so "can build" is the first two and use `can_build()`/`builders()` rather than `has()`/`owners()` for that question. **The namespace trap: 39 ids appear under both `Use Type: Unit` and `Use Type: Tech` — id 8 is Longbowman for BRITONS and `Town Watch` for the other 61.** Filter every lookup by `Use Type`; without it the reader reported Tarkan as owned by both HUNS and BURGUNDIANS and Berserk by both VIKINGS and LITHUANIANS, i.e. false positives indistinguishable from real sharing. Evidence the engine READS this layer: the exe contains the path template `CivTechTrees/%s.json` (offset 0x3261A18) and names **every** field (`Node Status`, `Use Type`, `Picture Index`, `Prerequisite IDs`) and every status/type value.
- **★ Prove offsets against a field the codebase already trusts, before measuring anything with them.** Deriving the `Enabled`/`Disabled` byte positions by hand, I dropped one byte and read `OldPortraitPict`'s `0xFFFF` as "HideInEditor", so **every unit reported 255** — a whole round of measurement would have been noise. The fix: check the derived offsets reproduce an already-captured field first (`icon_id`: 136,861 records, **0 mismatches**), then measure. **A probe must contain a check that can fail.**
- **★ Pick test samples whose answer you already know, or a false positive passes silently.** Tarkan reported as "shared by HUNS and BURGUNDIANS" looks exactly like genuine sharing; the only tell was that it contradicted a fact I was sure of (Tarkan is Huns-only). The regression test now asserts five civ-exclusive units are each owned by exactly one civ and **absent** from the other 61, and that the namespace filter *changes an answer* (unfiltered: 62 civs hold id 8; filtered: 1).
- **★★★ Writing that JSON layer is byte-exact and NOT a plain `json.dump`.** Use `civtechtrees.serialize` (never `json.dump`), which is `json.dumps(obj, ensure_ascii=False, indent=2)` → `replace("'", "\\u0027")` → `replace("\n", "\r\n")` → UTF-8, no BOM, no trailing newline. **The apostrophe step is load-bearing**: without it only **60 of 62** shipped files reproduce, because DANES.json and MAYANS.json write `Northmen's Fury` / `Hul'che Javelineers` with `\u0027` (the only unicode escape anywhere in the corpus). A near-match is the dangerous kind — it parses identically and still differs on bytes nobody asked to change.
- **★★★ A function serving BOTH read and write has its return shape as part of the output format.** `load_trees` originally reshaped each file into `{"units": [...], "buildings": [...]}`; reading was fine, but `serialize` re-dumps whatever dict it gets, so the emitted mod wrote `"units"` where the engine needs **`civ_techs_units`** — a file the game cannot parse. No reader test can catch it (reading never inspects key names); only an end-to-end test that reads the emitted file back from disk did. `load_trees` now returns the parsed document itself plus a `path` key, keyed by `UNITS_KEY`/`BUILDINGS_KEY`.
- **★ Granting a unit to a civ COPIES a real donor row — never invent a field value.** `grant(tree, node_id, source_row)` + `donor_row(trees, node_id)` + `revoke(tree, node_id) -> n` (0 is legitimate). Copying is schema-safe because `Unit` rows come in **10 different key sets**, so the row must be chosen by `(Node ID, Use Type)`, not by shape. Fields that never vary for a given node are safe to inherit (`Node ID`, `Use Type`, `Draw Node Type`, `Prerequisite IDs`); the ones that DO vary (`Node Status`, `Name String ID`, `Picture Index`, `Help String ID`, `Building ID`, `Age ID`, `Name`, `Link ID`) are reported as warnings so the UI can say whose wording it inherited.
- **★★★ The donor is chosen by MEANING, not by order: status → the row variant the MAJORITY of civs use → civ name.** "First able civ in sorted order" is deterministic and was WRONG: `ACHAEMENIDS` sorts first, is a Chronicles civ with its own localisation, and handed 112 tech grants the name `Exorcism` where the other 56 civs say `Faith` (same shape: `Flaming Arrows`/`Chemistry`, `Bastion`/`Keep`, `Target Practice`/`Ballistics`; unit side 3 grants, visible ones `Priestess`/`Monk`, `Palintonon (Packed)`/`Trebuchet (Packed)`). `_row_key(row)` excludes `Node Status` (two rows differing only in status carry the same presentation), and **status is only a tie-break because `grant()` writes `Node Status` explicitly — the donor's status is never inherited**. Civ name is the last key so the emitted mod never depends on dict iteration order. Audit is not code reading: put the candidate rules on one table (`_probe/probe_donor_rules.py` columns A/B/C). Whenever you use "sorted, take the first" to remove nondeterminism, ask again whether that order also means something to the user.
- **★★ A field that is valid for the donor can be meaningless for the receiver — and a generic warning buries it.** `Building ID` says where the thing is produced/shown. Measured: **1497 of 14687 unit grants (10.19%) and 224 of 10369 tech grants (2.16%) inherit a building the receiving civ cannot reach at all** (`reaches_building(tree, bid)` = the id appears as a `Node ID` OR a `Building ID`), and **no other donor fixes it (0 fixable)**. My guess that this clustered in the six Chronicles civs was **falsified by my own probe**: `node 45` appears as a row in all 62 civs but is used as a `Building ID` by only 56, and Chronicles accounts for just **3.2% (48/1497)** — the rest is spread over EVERY civ (~26 rows each). Hand-verified case: `ARMENIANS` never mentions `104` anywhere in its 173 rows (its own `Monk` reads `1806`), so a granted Missionary (Spanish donor, `Building ID=104`) has no Monastery. It gets **its own sentence**, not a slot in the six cosmetic `inherited ...` warnings. Also: the first draft of that count cited an earlier research probe's 1659/253 — **a cited count must be re-run from the shipped predicate.**
- **★ `emit_data_mod` takes `json_files` and `dat_bytes=None`; use `emit_json_mod` for a JSON-only change.** A per-civ availability change touches no `.dat` byte, and shipping a byte-identical `.dat` would waste ~12 MB and hide the real change. Both entry points share one emitter so the path/overwrite/redundancy/manifest rules cannot drift. Two traps found by the e2e test: (a) with `dat_bytes=None` nothing created the mod directory (`FileNotFoundError` on `info.json`) — "this path needs no X" is not "this path needs no X's side effects"; (b) a shipped JSON file that is byte-identical to the base **pins it to today's content** and silently reverts a future patch, so it is reported as `json_identical_to_base`.
- **★ How do we know this JSON layer is mod-overridable?** Chain of measurement, not analogy: (1) real published mods write into `resources/_common/dat/` — `550749` and `551103` both ship `linkedTechs.json` (4,203 B vs the base 3,947 B) and `297820` ships `civilizations.json`; (2) overrides DO resolve at nested paths inside a storage point — 550 installed mod files sit 2–4 levels under `widgetui/` (e.g. `widgetui/textures/ingame/emblems/achaemenids.png`), and only 8 files sit at depth 0 under DAT; (3) the game's own `modes/Pompeii/` substitutes 17 `CivTechTrees` files, 3 of which differ from the base ones. **Still unproven: no mod on this machine ships `CivTechTrees/`, so it has never been observed in game.** Do not upgrade that to a claim without an in-game load.
- **★ A fragile string heuristic must not drive a design decision.** Deciding whether the mode's CivTechTrees is an overlay required matching `.dat` civ names (`Egyptian`, `Carthage`, `Lac Viet`, `Hittite`, `Palmyra`) against plural file names (`EGYPTIANS.json`, `CARTHAGIANS.json`, …). Three different normalisations gave three different answers (15 / 4 / 2 civs "with no file") and flipped the verdict each time. When a heuristic's output changes the conclusion, the heuristic is the wrong instrument — go get direct evidence instead.

## Guardrails that are easy to violate

- **Never hardcode an offset or a field width.** The authoritative per-field order is the vendored C++ in `_probe/source/genieutils/` (`include/genie/dat/` headers + `src/dat/*.cpp`). Derive widths from the source, mechanically.
- **Version-aware or wrong.** `VER 8.9` → `GV_C32`; `VER 7.8` → `GV_C21`. 16 guards differ between them across 6 source files. `parse_dat.py` reads a `gv` attribute at ~27 branch points; **any hand-rolled lightweight reader must expose `gv` too**, or it silently computes wrong offsets. Pass `gv=p.r.gv` from the authoritative parser — never a literal.
- **Per-civ unit copies are independent physical records.** Editing "the Archer" means **63 separate byte writes**. The tool must apply to all civs by default. Membership is *not* always 63: 2,693 distinct unit ids, only 2,164 present in all 63 civs (Gaia carries 529 extra eyecandy). Query membership per civ; never assume 63.
- **Civ differences live in Tech/Effect data, not per-civ unit records.** All 62 playable civs' unit attribute blocks are byte-identical (sha1_16 `b07fdd0136fce6f9`); only Gaia differs (`ee8a4122df26cc5a`).
- **Width discipline is load-bearing.** `HitPoints` is `i16` at unit offset +22; overflow silently corrupts the next field.
- **Changing a value is safe; changing a count is geometry.** Container `i16 count` fields shift everything after them. In-place patching cannot add/remove units, civs, or techs — use the full re-serializer for that.
- **Compression is not reproducible byte-for-byte.** Do not verify by "recompress and compare". Verify by **re-parsing with the unmodified parser** and asserting exact EOF + leftover 0.
- **Writer bugs hide behind never-executed branches.** The `RandomMaps` segment is empty (`count 0`) in all 5 real datasets, so its read/write width mismatch was latent for a long time. Test unexercised branches against synthetic bytes built from the C++ layout: `_probe/datparse/test_random_maps.py` does exactly this and asserts reader-consumes-all **and** writer-reproduces-bytes (count 1/2/3).
- **A `w.op(n)` width error cascades into an infinite loop.** `op(n)` copies `n` bytes from a *raw* cursor, so under-reading desyncs that cursor; the writer then reads a garbage `count` and loops forever. **A hanging test IS the width-bug signal** — don't dismiss it as a flaky script. (Fixed: `_write_map_unit` emitted `op(10)+op(32)`=42 B; authority `RandomMap.cpp:214-229` is `4+4+1+1+2+32`=**44 B** → `op(12)+op(32)`.)
- **Check for `static` before porting C++ state machines.** `MapInfo::io_all_` (`RandomMap.h:147`, `bool io_all_ = false;`, **non-static**) is per-instance, so `serializeSub<MapInfo>` running twice (pass 0 = headers, pass 1 = bodies) requires a per-**pass** flag. A shared flag that toggles *inside* the map loop only coincides when `count <= 1` — a permanently-green test class. The reader already tracked it per map; the writer did not.
- **Stale comments poison later diagnosis.** `read_map_land`/`read_map_unit` carried `# 47 B` / `# 46 B` while both actually consume 44 B. The numbers were wrong, the code was right — and the wrong comment misled a later investigation into hypothesising a phantom reader bug. When a comment quotes a width, verify it against the source and fix it.
- **Sweep the whole read/write width class mechanically — don't wait for the next coincidence.** `_probe/datparse/sweep_read_write_widths.py` pairs every `read_X` with `write_X` / `_write_X`, drives both counting shims from the same zeroed input, and compares consumed vs emitted bytes. Result: **`pairs=41 agree=41 differ=0 error=0` on both `GV_C32` and `GV_C21`** — so after the `_write_map_unit` fix there is no second width mismatch. Two things that made it work: (a) try **both** writer naming conventions (`_write_` first attempt found *zero* `map_*` pairs); (b) a reader taking extra context (`read_terrain_restriction(r, terrain_count)`) needs a whitelisted neutral arg. Internal control: version-sensitive pairs really do move (`train_location 9→5`, `type50 86→70`, `unit 188→192`), which proves the sweep exercises the `gv` branches instead of running vacuously.
- **When one run reports a whole batch of failures, suspect the harness first.** The sweep's first run reported 12 AttributeErrors across 12 functions; all 12 were missing shim methods (`skip`, `debug_string`), not 12 real bugs. The counting shims must expose `skip(n)`, `raw(n)`, `debug_string()` (reader) and `debug_string(s)` (writer, `u16 marker + u16 len + bytes`, **no `+1` NUL**).
- **A zero-difference result is only meaningful if the control input can actually vary.** State the boundary: the sweep covers *width*, not value-driven variable-length structures. Zero hits here makes that distinction moot, but it would have mattered otherwise.
- `parse(stop_after=N)` **raises `SystemExit(0)`** — it kills the interpreter, not returns early. Never call it in a process that needs to continue.
- **A reported list must be the PROJECTION of the compiler's own chooser, never a filtered copy of the stored list.** `describe()`'s cost list is built by `compiler.cost_report()`, which calls the very `_pick_cost_slot()` that `_targets_for_tech`/`_targets_for_unit` call. Filtering the stored slots instead hid **119 writable tech slots** (all on the fallback path onto a wholly empty `(t,0,0)` slot — techs 20/1210/1211/1270) and showed 10 slots no intent could name. Both directions are silent lies. Same for stats: `compiler.unit_field_values()` walks the schema so "reported" and "writable" cannot diverge.
- **"Is it reachable?" is `edit_count > 0`, not "did `plan()` raise".** An unreachable target returns `edit_count 0` plus user-facing prose (`骑士 has no 成本 wood to change`) and **never raises**. A test that reads the exception calls every field reachable and passes while testing nothing — this bit `test_api.py` twice.
- **A resource `type` with no name is REPORTED, not dropped and not misnamed.** Unknown types (7/506/508/513 on techs; 214/215/501/514 on units) go to `stats["unmapped_costs"]`; the unit path used to silently discard 17 real costs, so a player could be charged a resource the panel never showed. Nothing in `stats["costs"]` may have a resource name starting with `type`.
- **★★★ THE WRITER IS ONLY EQUAL-WIDTH UNLESS YOU TELL IT OTHERWISE.** `Writer._emit(b, kind, raw_len=None)` advances **both** cursors (`pos` and `rpos`) by `len(b)` when `raw_len` is omitted. That is correct for every in-place patch this project made for fifty rounds, and wrong the moment a field's width changes: lengthening one graphic record's `file` string by 3 bytes produced **991,273 model/raw mismatches and a file 3,065,258 bytes too big**, then a reparse that died in `read_bird` with `struct.error`. Pass `raw_len=` (from `Reader.last_string_len` / `_file_len`) whenever a string or any variable-width field changes size. **The failure is a size explosion, not an exception**, so verify by byte-count and exact-EOF reparse, never by "it wrote something".
- **★★ `Reader.debug_string()` returns `(marker, text)`, not `(length, text)`.** Reading the marker as a length steps the cursor by whatever the marker bytes happen to be (2,656 in one measured case) and breaks even a **zero-edit** round trip — the loudest possible signal, if you look for it. The stored byte count is `Reader.last_string_len`; any hand-rolled reader passed into `read_*` must set it too (same duck-type contract as `gv`).
- **★ An unnamed cost type gets the game's own name, and stays a bare number only for slots the game itself reserves.** `resource_labels.json` (328 ids) is built from the game's **own** resource-name block: string id `15000 + resource type id`, contiguous 0–550 in `resources/<locale>/strings/key-value/key-value-strings-utf8.txt`, in **every** locale (en/zh/tw), 551 slots of which 328 are named. It **replaces AGE's `[AoE2DECivResourceNames]`** (271 names), which could not name `501`/`506`/`508`/`513`/`514` **at all** — five types the shipped data actually charges. Where the two disagree the **game wins**: the game calls 215 `Bonus Forager Food`, AGE calls it `Mercenary Kipchak Limit`, and that AGE phrase occurs **nowhere** in the game's 19,677 strings. AGE is deliberately **not** a fallback source: every id it could add is one the game marks `Unused Resource NNN` (it calls 34 `Faith`, 194 `Crenellations`). The 223 `Unused Resource` slots are **dropped**, so an id the game does not name keeps its raw number rather than inheriting a meaningless label. Ids 0-3 ship with a leading `!` (the game's suppression marker, only 4 strings in the whole file); strip it for display. **`name` is an ADDITION, never a replacement** — the raw `type` is always retained, and a "has a name" entry must never be an empty string (that reads as "named, and the name is blank"). **Naming an id is NOT making it editable**: `resource_labels` and `resource_types` are different tables and must not be wired together. Those eight types are engine counters and local-upgrade pseudo-resources — measured amounts are `1`, tech-side `1/2/3/4` (Relics Captured), and **`-1` on type 215** (a "cost" of minus one can only decrement a counter) — so they belong in the UI as an *explanation* of a slot (`需求：军事执政官建造限制 ×1`), never as a new chargeable slot. `_probe/test_declared_resources.py` asserts they stay undeclared so this has to be argued, not rediscovered.
- **★ Build a translation table's filter from the SOURCE language only.** `drop_unused` decides which slots are nameable from the **English** text and lets every other locale merely *translate* that set (`zh = {k: zh_all[k] for k in en if k in zh_all}`). Applying the English predicate to the Chinese file matches nothing (zh writes `未使用的资源 NNN`), so it would **ship 551 "names"** including the unused ones. Guard it: both locales must yield exactly 551 contiguous slots or the `15000 + type` scheme does not hold.
- **`airesourcetypes.json` looks like a resource-type table and is not one.** Its `ResourceTypes` holds 4 entries whose `ID` is an **object** id (Forage Bush 59, Gold Mine 66, Stone Mine 102, Tree 284), not a resource-type id. **Decide whether a table is usable by whose key space it is, not by its filename.**
- **The two cost enums are deliberately not identical.** `tech.cost` offers food/wood/gold/stone — **no tech in BASE pays population** (type 4 appears 0 times across 1,510 techs), while `unit.cost` does (House/Villager, 1 pop). Assert the union covers `resource_types`, not that each enum equals it.
- **Measure the blast radius before tightening a selection rule.** Requiring `flag != 0` on the cost fallback looked like a clean fix and would have closed **119 writable tech slots** (including real techs 20/1210/1211/1270) to "fix" one unit slot.
- **User-facing text must never leak a locator key or a raw slot number.** Previews read `bindings[...]["label"]` ("成本 gold", "射程"), never `name` (`max_range`) or `"cost type 3"`. Assert the raw token is **absent** from the string, not merely that no `None` appears.
- **A message that enumerates its own cases becomes a lie the moment a field is added.** The negative-value refusal used to read "Cost and time cannot be negative"; once `max_range`/`reload_time` were routed through the same `non_negative` guard it was refusing a negative *range* while naming costs. It now states the conclusion only — the schema flag is the real definition. Same class as a stale width comment.
- **`plan()`'s intent selector key is `"intent"`, not `"kind"`.** `kind` is itself a *field* of `unit.attack_class` (`attack`/`armour`), so using it as the selector fails as `unknown intent None` — a message that reads as plausible. `plan()` returns `description` (prose), not `resolved`; `describe()["stats"]` holds **one entry per declared `unit.stat` field plus a separate `costs`** key — so its length is `len(declared options)`, never a literal (it was 11 before `min_range`/`accuracy` were added; assert against `schema()["intents"]["intents"]["unit.stat"]["fields"]["stat"]["options"]`).
- **The installed mod list IS the `Mods` array order.** `screeninstalledmods.xaml`'s listbox has no `SortDescription`, and `IDS_MODMGR_PRIORITY_EXPLANATION` defines *higher in the list = wins file conflicts*. So: **never re-sort the array by `Priority`** (that silently rewrites an order the user set in-game), and when updating an existing entry change only `Enabled`/`Title` — do not move it. Renumber `Priority = index + 1` afterwards so the order is stable under either "engine walks the array" or "engine sorts by number".
- **Writing `mod-status.json` is a byte-format contract.** Compact JSON (`separators=(",", ":")`), UTF-8, **no BOM, no trailing newline**, top level `{"Mods":[...],"Unsub":[]}`, entry key order `CheckSum, Enabled, LastUpdate, Path, Priority, PublishID, Title, WorkshopID`, `CheckSum`/`LastUpdate` as **strings** (the latter 13-digit milliseconds), `Enabled` a real bool. Local mods live at `<profile>/<account>/mods/local/<name>` and their `Path` is `local//<name>` (exe string `local//%s`). **Back the file up before writing**, and prove in tests that the *real* profile was never touched — `install` rewrites the user's whole mod list.
- **`build` and `install` are separate on purpose.** `build` is reversible and writes to a folder you own; `install` changes which mods the game loads. Keep them distinct at the API, and make the caller opt in.
- **A field key and a mark name are different namespaces — never diff them.** `unit_fields["movement_speed"]` is bound to mark `speed`, and `creation_time` is bound to `train_location` rather than any mark. A first audit that compared binding *keys* against mark *names* produced a confident, entirely fake finding ("2 unbound marks, 3 unmarked fields"); the second audit resolved per `(source, name)` and reported **`UNRESOLVABLE BINDINGS: 0`** for both unit and tech. Only 10 distinct marks exist across 136,861 unit records. Generalisation: **a probe that compares two identifier sets will always produce numbers — make it resolve names to offsets before believing the count.**
- **"Easy to bind" is not "should become an intent".** The 27 commented bare reads in `locate.py` include several fields with plenty of signal — `attack_graphic` (743 distinct values, 51.7% non-default), `projectile_unit_id` (69 distinct, 17.4%), `frame_delay` (30 distinct, 14.0%) — that are deliberately **not** exposed: the first two are *references to another entity* (changing them needs a "target must exist" guard) and `frame_delay` has no authoritative semantics. Only `min_range` (8 distinct, 6.3%) and `accuracy` (19 distinct, 69.3%) went in, because each is a plain scalar on its own record. Ask two questions before binding: **is there signal** (distinct / non-default ratio) and **is the value safe** (scalar vs cross-entity reference). Record the rejected ones as capability notes rather than binding them and finding out later.
- **A test helper that asserts success by default will fail your failure test — with its own message.** `test_compiler.py`'s `run(label, intent, expect_ok=True)` asserts compilation succeeded, so a refusal case written as `try/except` around it dies at `AssertionError: expected this intent to compile`. Pass `expect_ok=False` and assert the helper returned `None`. Same family as `edit_count > 0`: **if the direction of the assertion is written backwards, the test passes or fails for the wrong reason.**
- **Never prove a write path by writing back the value that is already there.** The archer's shipped `accuracy` IS 80, so `value=80` claimed 63 edits while changing **zero bytes** — green, and testing nothing. Use `80 -> 65` and additionally assert `{e.before} == {80}` so the baseline moving would be caught. This is the same trap as hash-comparing a compressed `.dat` against a raw one.
- **★ A flag in the schema is not a flag in the code until no call site can bypass it.** `signed` sat in `dat_bindings.json` from the beginning and **every write path hard-coded `signed=True`** — `compiler._write_targets`, `api.build()`, and `tests/test_emit_mod.py` each carried their own copy. Binding the first unsigned field (`garrison_capacity`, a u8) would not have produced a wrong message, it would have raised `OverflowError` on the first value above 127. Read the flag at the point of use: `_signed(b)` → `Edit.signed` → `compiler.apply_edits()`, which is now the **only** implementation of "Edit → bytes". Same family as `non_negative` being swallowed by the float early-return, and as the read side hand-listing its fields. **After fixing a flag, grep every write site and confirm exactly one implementation remains** — a surviving copy will reintroduce the bug.
- **★ Never let a test reimplement the logic it is checking.** `test_emit_mod.py` packed edits with its *own* `signed=True` loop, so it validated the product using the product's own bug. Any duplicated logic inside a checker is a structural blind spot: route both through one function (`apply_edits`) and the checker starts testing the real path.
- **★ When fixing a flag, ask who else is judging an inner object by an outer one.** Mirrors (`displayed_range` → `max_range`) were validated against the **outer** binding's `non_negative`/`label`, not their own schema entry — a same-family defect that was not in the original task. `_targets_for_unit` now yields the target's own binding, not a bare boolean, so each target is judged by its own declaration.
- **★ Establish a control group before claiming you "fixed a bug".** BASE's 88 non-zero `garrison_capacity` records max out at **30**, so `signed=True` never failed on today's data — this was a latent landmine, not an existing corruption. The two claims mean very different things to a user; the control (`records with a value > 127: 0`) is what lets you say which one you have.
- **★★ A vocabulary file generated from a multi-engine source is only correct if you evaluate its branches.** AGE's `Lists.cpp` fills `effect_attribute_names` / `class_names` / `effect_type_names` with `if (GenieVersion …) … else …` and each engine's names land in the *same* C array. The old scraper grabbed every `.Add("…")` literal and keyed a dict by the number in the label, so **later branches overwrote earlier ones** and the shipped tables described Star Wars: Galactic Battlegrounds: attribute `104` was `Carbon Costs` (DE has `Wood Costs`), the whole class table was shifted one slot and ended with `50 - Jedi`, and four UP-only command types (`9/19/29/39 Set Player Civ Name`) existed that DE cannot encode at all. The fix is `_probe/schema/cpp_branch.py`: a statement-level evaluator that walks the real `if/else` with `GV_C32 = 54`, `GameVersion = EV_DE2`, `isAoE2DE = true`, and **raises `UnsupportedCondition` on anything it has not modelled rather than guessing**. Tables are now regenerated, not hand-copied, and `sync_engine.py` refuses to vendor a table whose `note` lacks the `walked AGE's own version branches` marker. Cross-check any vocabulary change against the `.dat` itself — `attribute 104`'s users are literally named `C-Bonus, TC Wood cost`.
- **★★ The class table is keyed by the number in the LABEL, not by list position.** `armor_classes.json` indices are only coincidentally the same as the ids: an entry reading `19 - Trade Cart` lives at slot 19 *because* `18 - Monk` is missing from the AoE2 branch (the older AGE label `18 - Priest` collapsed onto the same key). The decisive evidence is the data, not the table: Archer's `Class` field is `0` and its bonus techs target `B = 0`, and class `4` is Civilian (Villager) while `6` is Infantry (Militia). Render an id the table cannot name as `Class <n>` — never renumber it into a neighbouring slot.
- **★★ A tech's effect is a SHARED record; editing it changes every tech that points at it.** A tech stores an `i16 effect_id` indexing the top-level Effects array (1,180 of 1,510 techs point at one; 330 do not). 37 effects are referenced by more than one tech and **34 of those carry commands** — `effect[470]` is shared by 11 techs. Any preview must report `fan_in` / `shared_with` rather than let the user discover it. Also: the Effects array has **no offset marks at all** in the parser (0 `r.at()` calls), so writing an effect required adding `walk_effect`/`locate_effects` — and it deliberately marks only the five command fields, never the effect name or the command count, because those change record length and shift every later `effect_id`.
- **★ Address an effect command by INDEX, not by meaning.** Attribute `8`/`9` pack a class into the high byte of `D` (`class = D >> 8`, `value = D & 0xFF`, and the low byte is **unsigned**), so `1025.0` is "class 4, value 1". Several techs carry two commands with the same `(attribute, target, operation)` triple but different values (a food cost first `×1.174` then `×0.800`) — a semantic address would have to guess. Writing the value back must preserve the class byte (`encode_effect_value`), or the command silently retargets class 0. The vocabulary covers 89 attribute ids and 55 command types; a modifier attribute the table cannot name is reported read-only with a reason, not hidden.
- **★ "Bytes changed == fields changed" is wrong for the fifth time.** `15.0 → 20.0` moves exactly **one** byte (the second significand byte). Derive expected byte counts with `struct.pack` and locate an edit by its **value**, never by assuming `diff[0]` is the field's first byte — it is the first byte that *differs*, which for a float is usually the second.
- **★★★ "Where the most data is" is not "what the user asked for": test a candidate mechanism by CONTRAST, not by presence.** The refused-family backlog ranks `type 2 Enable/Disable Unit` second by "new techs it would unlock" (169), and it reads like "unlock a unit" — so it looks like the missing half of `unit.availability`. It is not. **War Galley has 56 builders and not one owns a type-2 enable** (a tree row alone is enough), while **Hand Cannoneer is blocked for 38 civs and all 38 own an enable** (owning one grants nothing) — so the command is neither necessary nor sufficient, and the per-civ gate is the `CivTechTrees` row. A type-2 command is a **global** lever; never document it as "let civ X build unit Y". Pinned by `_probe/test_mechanism_gate.py`. **The general rule: when two mechanisms are both present in the data, presence proves nothing — find a case where they disagree and see which one predicts the outcome.** When grouping rows into "regular" and "irregular" to assert on them, the predicate that *selects* a group is the one to reuse when *searching* it (`raw[2] in (0,1)` finds nothing inside a group defined by `raw[2] == -1`).
- **★★★ An always-true predicate produces empty cells, and empty cells look like a law.** The same contrast run on `type 3 Upgrade Unit` reported `can_build+no_upgrade = 0` and `cannot+no_upgrade = 0` — reading as "owning an upgrade is necessary". It is an artifact: most type-3 commands sit on **global** techs, so "this civ owns an upgrade into B" is true for **1816 of 1896 (95.8%)** of (civ, target-row) pairs, and that column must be empty. **Print a predicate's truth rate before reading its cross-tab; a table can only discriminate when both directions have samples.** The same run also picked the **wrong dependent variable**: an upgrade target is something you upgrade *into*, not something a building trains, so every apparent disagreement among the 109 civ-owned-only targets was a `builders == 0` row (House, Castle, town-centre variants, Polemarch). **If every "contradiction" sits where the dependent variable is zero, suspect the dependent variable.** And a probe's VERDICT paragraph must match the table it printed — one here asserted both directions the data did not support, and the next reader quotes the paragraph, not the table. Pinned by `_probe/test_type3_scope.py`.
- **★★★ "This family overlaps a shipped intent" must be measured, and the measurement usually says the opposite.** The four remaining tech-side families look like the most obviously redundant ones — `tech.cost` / `tech.research_time` are already writing techs. They are not: `type 101`/`103` modify **another** tech (172 of 175 rows, 68 of 71) conditionally on the **carrier** being researched, and the carrier is civ-owned for **144** of 175 and **60** of 71. The shipped intents write the target's own record **globally**, so nothing can say *"researching X makes Y cheaper for this civ"*; only their 31/11 global-carried rows are indirectly reachable today. And **`type 102 Disable Tech` is not a second spelling of a tree row** — that tempting claim is FALSE on **64 of its 81** civ-carried rows, where the civ's tree OFFERS the tech (`ResearchedCompleted`) and the command REMOVES it (26 self-disabling, 55 sibling, **46 mutual** — the Chronicles choose-one-of-two unique techs: Sparabaras/Reed Arrows, Taxiarchs/Trierarchies, Helot Levies/Xyphos). A tree row states per-civ availability; it cannot state *"available until you research the other one"*. `type 8` is not even the same class — its slot D spans `0..418073`, a **string-id** space. All four stay refused, each for a **different stated reason** (undetermined operation codes; unobservable precedence), and this is pinned by `_probe/test_tech_side_families.py`.
- **★★★ Writing a probe's conclusion BEFORE its table is a defect, not a style slip.** Rounds 29 and 30 both did it: `probe_type3_contrast.py` asserted causality its table did not show, and `probe_tech_side_verdict.py` asserted "102 is a tree-row alias" while its own Q2 table printed **64 counterexamples** — a claim refuted inside the same file. The same wrong sentence was also pre-written into `compiler.py`'s module docstring, where it would have misled the next implementer. **A conclusion paragraph must either be printed after the table and derived from it, or be labelled "not yet measured".** And when a documented claim turns out false, fix the **documentation** — a wrong sentence in a docstring outlives the bug it caused.

## Data-mod reality (from real published mods)

Real data mods change **only the back half**; bytes before `0x36B0BE` (the `numEffects` field) are identical, including all graphics. Growth comes from **adding** placeholder unit/tech objects, not from editing values — one "10x resources" mod adds 2,341 empty eyecandy units and 4,354 tech placeholders per civ while changing **zero** existing unit stats and leaving the civ Resources array untouched. A UI must be able to distinguish these filler objects from real content.

## ★★ The build-panel layer is a PAIR of files, not one

`resources/_common/dat/futuravailableunits.json` covers **58** civs. A second file, `paphosfutureavailableunits.json`, covers **12** more (6 real civs + 4 placeholders `Paphos6..9`). Union **68**; the tree has **62** civs (all playable, incl. the six antiquity ones). Together the pair covers every civ that has a tree — so "the menu might read the panel" stays live for *every* civ.

- **Which file to write is derivable, but you should still ASK.** `civilizations.json`'s `era` field has exactly two values: `base` (**57** civs) → main file; `antiquity` (**6**: Achaemenids, Athenians, Macedonians, Puru, Spartans, Thracians) → paphos file. The split is clean, with no counterexample — but agreement is **corroboration, not the answer**. `api._panel_availability` uses `panel_path_for()` (which looks at which file actually lists the civ); a civ no file lists is **reported, not guessed**, and its tree edit still ships.
- **Use `buildpanel.panel_path_for(game_root, civ)` — ask, do not infer.** The two files share keys (`FullTechCiv`, `Gaia`) and `FullTechCiv` differs between them (31 units only in main, 22 only in paphos). A plain dict merge over both (`load_all`) silently loses one version; records now carry `sources`/`ambiguous` so the loss is visible.
- **This does NOT mean the tree needs an era-selecting directory.** `CivTechTrees/` holds **62 files covering all playable civs** (antiquity included) — one flat directory. **Before copying a selector rule to another layer, check whether that layer is one-file-per-civ or one-file-for-many.** The panel is scoped per era; the tree is scoped per civ.
- **`buildpanel.py` IS wired into `api.py` now — and an availability build ships BOTH halves.** `aoe2mod/api.py`'s `_panel_availability()` calls `buildpanel.availability_edit()` on every availability edit, next to the tree edit, so one `build` emits `CivTechTrees/<CIV>.json` **and** the panel file. Four shapes are pinned by `_probe/test_panel_wire.py` (28 assertions):
  1. **the panel already lists the node** (11 shipped (civ, unit) pairs are exactly this: the tree says `NotAvailable` and the panel lists it) → an **honest no-op**: `mode: "none"`, and **the 1.3 MB panel file is NOT emitted**. Do not "fix" this by always emitting — and do not let the report claim a file was written when it was not: `api` prints a different `proven` sentence for the no-op case for exactly that reason.
  2. **the panel lacks it** → an entry is **synthesised from a measured donor** (`buildpanel.synth_entry`), placed under the **receiver's own tree row `Building ID`**, with `RequiredAge` taken from the **receiver's** `Age ID` (not the donor's, or the menu gates it at the wrong age).
  3. **a revoke** → `remove_entry`, one entry out.
  4. **the receiver has NO tree row** (common in the TECH space: Goths has no Yeomen row) → `row_for` returns `None` and there is no local `Building ID`. Fall back to **`CT.donor_row`**, the same donor the tree layer copies from, and record it as `building_from`. **Without that fallback a legal grant is refused with "no building is known for this node" — a lie, since Britons has it.**
- **There is no `panel_edit` on the plan side, and the plan must stay that way.** `plan()` reports what is editable; the panel half is decided at build time because a plan cannot know whether the panel already lists the node without reading 1.3 MB. The report distinguishes the cases (`mode`), which is what a UI needs.
- **And note what the panel is NOT: it is a shipped artifact, not a runtime cache.** Its mtime matches the `.dat`/tree unpack, the exe is 19 days newer, and **11 game launches have not rewritten it**. So the 2026-10-14 "editing the tree changed nothing" result is **not** evidence against the tree — if the menu reads this shipped file, editing the tree *could not* have moved the menu. That result is now **unproven**, not **disproven**. (`_probe/probe_panel_provenance.py`) **No test has yet shipped a panel file, so neither half has a positive in-game result. Both `not_proven` sentences in `api.py` say so; keep them that way.**
- **⚠⚠ `RequiredAge` in a panel entry is an AGE GATE, and it made one in-game test prove nothing.** The panel entry's `RequiredAge` equals the tree row's `Age ID` in **2819/2826 (99.75%)** of shipped entries. `Hand Cannoneer` (unit 5) carries **`RequiredAge: 4`** — the Imperial Age — for *every* civ that can build it, including Turks. So the 2026-10-14 test "grant Hand Cannoneer to Britons, open the game, the Range does not show it" **cannot have shown it**: a game starting in the Dark Age gates that entry at Age 4 no matter which file the menu reads. The panel write itself succeeded (7 entries → 8; the added entry is byte-exact). **Before choosing an in-game subject, check the subject for its own gates — an age gate, a research gate, a building gate — because a gated subject disguises "you have not met the condition" as "the write did nothing".** This is the second in-game test this project lost to a confound.
- **★ The clean subject for a panel test is `Champi Scout` (unit 2550, INCAS).** Tree row: `ResearchedCompleted`, **`Age ID: 1`** (Dark Age), `Building ID: 12` (Barracks). Shipped panel lists it in `Incas`/`Mapuche`/`Muisca`/`Tupi` under **building 12**, verbatim `{'ID': 2550, 'Name': 'Champi Scout', 'RequiredAge': 1}` — Units space 4, Techs space 0. **`BRITONS` has no row for 2550 at all**, so granting it to Britons is a real state change with no age gate.
- **The panel covers 30–31 buildings per civ — it is the tech-tree PREVIEW, not the villager build menu.** Castle (82), Wonder (276), Dock (45), Barracks (12), Range (87), Stable (101) are all in it. Pick a subject under a building the panel actually models.

### ⚠ A probe that names a mod folder breaks the moment the mod list changes

`_probe/probe_install_safety.py` used to hardcode `aoe2mod Smoke HP+Units` / `aoe2mod Smoke2 BuildPanel`. Installing a new smoke mod made it die with `FileNotFoundError` — reporting a stale path as if the game install had been damaged. It now **discovers** the mod carrying the edit under test (`_find_mod_with_fu()` parses each mod's panel copy and claims the one that actually carries the edit; `_find_mod_with_tree()` claims the one larger than the game's), and prints **`[SKIP]` while still running the game-side assertions** when nothing claims it. **The invariant is about the GAME's bytes and holds whether or not any mod exists — so a missing mod must downgrade one section, never the whole probe.**

### ★★ The cheapest tree-vs-panel experiment needs NO MOD AT ALL

The shipped tree and the shipped panel **already contradict each other** on a small, enumerable set of (civ, unit) pairs. That removes every loading/layering confound in one stroke: nothing is layered, so "did the mod load / did it win" cannot arise.

- **kind P — the panel lists it, the tree says `NotAvailable`: 11 pairs.** A visible button proves the menu reads the **panel** (the tree cannot supply it). All 11 are at **Imperial Age** except one.
- **kind T — the tree grants it, the panel is silent: 3 pairs** (`GEORGIANS`/`SICILIANS` unit 588 at the Siege Workshop; `SPARTANS` unit 13 at the Dock). A *missing* button proves the panel drives the menu; a visible one points at the tree.
- **No civilization has both kinds**, so a single game cannot show all four cells — but one observation per game is enough.
- **Recommended subject: Jurchens → Castle Age → Barracks → is there a 长剑士 (Long Swordsman, unit 77) button?** Tree says `NotAvailable`, panel lists it at building 12 with `RequiredAge: 3`. Present ⇒ the menu reads the panel; absent ⇒ it does not. Pinned by `_probe/test_zero_mod_experiment.py` (which also asserts **no ENABLED mod ships a tree/panel/dat file**, so the run stays clean).

### ⚠⚠ Three ways a mod-based experiment dies that have nothing to do with the write

An adversarial audit of a purpose-built discriminating mod (`_probe/team/auditor/REPORT.md`) found it unusable, and every reason generalises:

1. **A sibling mod shipping the same paths makes the control worthless.** The mod under test and an unrelated local mod shipped the **same three engine paths** with different content, and their `.dat` files were **byte-identical** (same sha256). "Villager HP 1000" then proves *a* villager-HP mod loaded, not WHICH. **Give the control a value unique to the mod under test, and check for siblings that touch the same storage points first** (`_probe/probe_enabled_mods_clean.py`).
2. **A subject can be masked by the design's own precondition.** Removing `Militia` (74) from the panel is unobservable for Britons because the **tree** already grants it — the button appears from the tree either way. **Before choosing a "remove it" subject, confirm the OTHER layer does not already supply it** (the shipped-wide figure is 491/495 masked).
3. **An outcome-to-hypothesis table that is not injective is not a test.** "Tree-only button present" ← tree drives **or** the two layers are unioned. If two hypotheses predict the same observation, add a third probe or state the ambiguity in the pre-commitment rather than in the conclusions.

### ⚠ A mod folder that is merely *present* is not *loaded*

Copying a folder into `<account>/mods/local/` does **not** register it: the game writes `mod-status.json` itself, and a mod absent from that file's `Mods` list cannot be enabled in the mod manager. Verify registration by **reading `mod-status.json`** (and, after the fact, the `Enabling mod #0 (...)` lines in `logs/<newest>/MainLog.txt`) — never by assuming the copy sufficed. This is also why local mods appear only in the **second** mod-manager pass, long after the startup resource load.

### ⚠ `buildpanel.buildings()` returns BLOCKS, not ids — and the failure is silent

`buildpanel.buildings(obj, key)` returns the list of building **dicts** (each with an `ID` key), not a list of building ids. Iterating it and passing each element as `building_id` makes `building_block()` compare `blk["ID"] == <dict>`, which never matches, so `entries()` returns `[]` for **every** civilization — and a probe written that way reports "the panel is empty everywhere" or "no disagreement found" as if it were a finding. (`sorted(BP.buildings(...))` fails loudly with `TypeError: '<' not supported between instances of 'dict' and 'dict'`; the unsorted form fails silently.) Correct form:

```python
for blk in BP.buildings(obj, disp):
    bid = blk.get("ID")
    for e in (blk.get(BP.UNITS_KEY) or []):
        ...
```

**This is the fourth instance of one failure family in this project** — `diag_drift.py`'s structural blindness, the invisible `Reader.gv` reader, a `None` that flowed into a verdict, and now an empty list that read as a result. **When a probe reports 0 / empty / "none found", first ask whether it actually examined anything.**

### ⚠⚠ The panel file has TWO availability channels — "silent" must mean silent in BOTH

`futuravailableunits.json` lists, under each building, a `Units` array **and** a `Techs` array. A unit that arrives through an upgrade research is named in the **`Techs`** array (research it, then the unit becomes trainable) rather than in `Units`.

| civ | panel `Units` at bldg 49 | panel `Techs` at bldg 49 |
|---|---|---|
| GEORGIANS | silent | **lists 320** |
| SICILIANS | silent | silent |

`buildpanel.GATE_KEYS = ("PrereqTech", "PrereqIconSet", "PrereqIconIndex", "PrereqStyle", "PrereqStringID")` — **354 panel entries carry these** in the shipped data, so a gated entry is common, not exotic.

### ⚠ A candidate subject must be VISIBLE, and distinct from its counterpart

Two filters an availability-experiment subject needs, both learned by shipping a wrong candidate:

- **It must have a display name.** Unit **320** is `ARROW8` — `zh=None`, `en=None`, an engine-internal projectile. It sat in a candidate list because a panel entry existed for it, and it made GEORGIANS look like a single-game discriminator. Filter on `Entity.zh or Entity.en`.
- **It must not share a name with the other subject.** The shipped tree/panel disagreements are *variant-id substitutions*, so the two variants usually **share a display name**: GEORGIANS' kind-P 320 and kind-T 588 are both "Siege Onager"; SPARTANS' 2147 and 13 are both "Fishing Ship". Present/absent across the two separates *panel drives* / *tree drives* / *union* / *neither*. Pinned by `_probe/test_zero_mod_experiment.py` section F.

### ⚠⚠ `button_id` is a CHAIN index, not a grid slot — and the `.dat` is a superset

`train_locations` entries are `{train_time, unit_id, button_id}` where `unit_id` is the training building. Reading `button_id` as "the slot number" is **wrong**. Grouped for the Barracks (12):

| `button_id` | units sharing it |
|---|---|
| **1** | **16** — the whole militia line (`74 Militia → 75 Man-at-Arms → 77 Long Swordsman → 473 Two-Handed → 567 Champion`) **plus** 361 Nordic Swordsman, 894 Eastern Swordsman, 1040 Henry II, 1793 Roman Legionary, … |
| 2 | 4 — `93 Spearman → 358 Pikeman → 359 Halberdier` + 2449 |
| 3 | 1 — 882 Condottiero |
| 4 | **28** — Eagle line, Huskarl, Fire Lancer, Greek Infantry, Varangian Guard, … |

**A command-grid button IS a chain** (clicking it cycles the upgrades of its group), and `button_id` names the chain. **Any "sort the grid by `button_id`" reading is wrong.** Verify with: *is this value shared by a whole upgrade line?* Shared = grouping; unique = slot.

**Second, same-data finding: the `.dat` is a SUPERSET.** It trains **49** units at the Barracks (including every civilization's unique units); Britons' tree has rows for only **8** of them → **41 have no row in that civ's tree at all**. So "what can a Barracks produce" necessarily passes a narrowing filter (**49 → 8**), and the only candidates are the **tree** and the **panel**. That promotes the unanswered question from "corner disagreement" to **architecture**: *which layer performs the narrowing?*

Restated precisely for the Jurchens case (militia chain, `button_id = 1`): the tree offers only `74/75` (`ResearchedCompleted`) while `77/473/567` are `NotAvailable` — and the panel lists **all five**. So the observation must be "**can the swordsman line be upgraded to Long Swordsman**", NOT "is there a Long Swordsman button" — one grid button carries the whole chain and its label changes with research.

Pinned by `_probe/test_button_groups.py`.

### ⚠⚠⚠ A subject is decisive only if the "yes" layer supplies a COMPLETE path

This is the **fourth gate class** to cost this project an experiment, and I scored every one of them backwards first.

The kind-P framing is "the panel lists the unit while the tree says `NotAvailable`, so a reachable unit means the panel was read". But a panel entry can name a unit while **not** offering the research that produces it:

```
JURCHENS barracks 12
  panel Units : 74, 75, 77 Long Swordsman, 93, 358, 359, 473, 567, ...
  panel Techs : 197, 215, 222 Man-at-Arms, 429, 602, 875, 982
  77's upgrade tech is 207  ->  NOT in panel Techs
  75's upgrade tech is 222  ->  IS  in panel Techs
```

If the engine requires that research, **Long Swordsman is unreachable whichever file the menu reads** — so "absent" cannot distinguish the hypotheses. `JURCHENS 77/473/567` are all like this.

**The earlier round scored this the wrong way round**: it marked "upgrade tech absent" as *clean* and recommended the Jurchens subject. It is the **unusable** case.

Only **4 of the 11** kind-P subjects supply a complete path: `MAPUCHE 528`, **`MUISCA 359`** (upgrade 429), `POLES 691`, `WU 474`. The mirror check is required on the kind-T side too (there the "yes" layer is the **tree**), which leaves `SICILIANS 588`.

**Judgement: when both layers are claimed to say something, check that the evidence on each side is COMPLETE.** A subject missing a required intermediate step cannot be used — its absence is unattributable. The four gate classes, in the order they cost me: **age** (`RequiredAge`) → **research** (`PrereqTech`) → **channel** (`Techs` vs `Units`) → **upgrade tech** (the unit's own `Trigger Tech ID` must be reachable in the layer that is promising the unit).

Pinned by `_probe/test_decisive_subjects.py`, and `_probe/test_zero_mod_experiment.py` sections B/B2/H.

### ⚠⚠⚠ The two availability layers express "upgrade" with DIFFERENT mechanisms

Do not check completeness for both layers in the same id space — that mistake cost a round.

* `Trigger Tech ID` on a **tree unit row** is a `.dat` tech index (`588 -> 320 'Siege Onager'`). Only **2 of 136** distinct upgrade techs appear as a tree `Use Type: Tech` row (`.dat` 34 `War Galley` / 35 `Galleon`, which the tech tree really does show as `Warships` / `Heavy Warships`); the other **134 appear in 0 of 62 trees**. So a **tree** expresses an upgrade through the unit row's own `Trigger Tech ID`, and "the tree has no Tech row for 320" is **normal, not a hole**.
* The **panel** expresses the same upgrade through its `Techs` array (Sicilians building 49: `Techs = [96, 255, 257, 239]`).

Completeness therefore has to be written per layer:
```
panel is the promising layer -> the unit is in `Units` AND its upgrade tech is in `Techs`
tree is the promising layer  -> that unit row is ResearchedCompleted AND its chain predecessors are too
```
And the tree's Tech `Node ID` **is** still the `.dat` tech index — verified by name identity (132 rows agree outright; the 106 apparent disagreements are display-vs-codename, `'Crop rotation'` -> `'Crop Rotation'`, `'British Yeoman'` -> `'Yeomen'`). **A range test cannot tell "an index into the same array" from "a different numbering that happens to fall in range"; compare identity row by row, and remember that a name mismatch is often display-name vs internal-codename.**

Pinned by `_probe/test_trigtech_space.py`.

### ⚠⚠⚠ A mod writing under `resources/_common/dat/` MUST carry `empires2_x2_p1.dat`

Reported by the user in game, twice: a mod that overrides the DAT storage point without the `.dat` **stops the game from starting** (`m21855`「你的mod里没有empires2_x2_p1.dat，所以连开局都开不了」; the same intent launched fine once the `.dat` was added).

Corpus evidence (`_probe/probe_dat_only_defect.py`): **every** third-party mod on this machine that writes under `resources/_common/dat/` also carries the `.dat` — 5 of 5 — and the only copy without one was this project's own JSON-only test. The DAT storage point is also the only one flagged `use_modes_path_for_mods: true` in `modes/Pompeii/Pompeii.json`, suggesting the engine resolves that directory as a unit rather than per file. That is correlation, not proven mechanism, but the cost is asymmetric: carrying a 12 MB file is harmless, omitting it makes the game unlaunchable.

`emit_data_mod` therefore copies the base `.dat` in as a **carrier** when `json_files` reaches into that storage point and no `.dat` was supplied; without `base_dir` it **refuses** rather than emitting an unstartable mod. The manifest distinguishes three things: `changes_dat` (did any `.dat` byte change), `mod_contains_dat` (is a `.dat` file present), `dat_is_carrier`.

**And note what the tests taught here**: five suites asserted "a JSON-only mod ships no `.dat`" — i.e. the green tests were protecting the defect. When a user reports a runtime fact, it outranks an assertion that encodes the old behaviour; **fix the assertion, not the product**. Pinned by `_probe/test_dat_carrier.py`.

### ⚠⚠⚠ Data mods load WHEN A MATCH STARTS, not at launch — and priorities do not apply

The user's correction (m24660), verbatim: 「开启游戏只要没有进入对局是不会加载数据模组的，只要数据模组放入文件夹，就是默认启用的，在开局前将其选中并进入对局才会真正加载模组，所以你才没必要去所谓的启用模组和放到优先级1，因为完全不会有任何影响。」 Plus (m24720): 「游戏只会加载一个数据模组，以及是用户自己手动选择的，所以不会被优先级影响」.

So for `.dat` work:
* **Do not** write `mod-status.json`, flip `Enabled`, or set `Priority` — none of it affects whether a data mod loads. A data mod just has to be in `mods/local/` and be **selected before the match**.
* `Priority` serves text/graphics mods (they are overlay layers). Only **one** data mod is loaded, chosen by the user.
* `mod-status.json`'s `Enabled` flag says nothing about whether your `.dat` is in effect.

**This cost eight wasted in-game tests.** The log line `Enabling mod #0 (X)` is a late `mods/local/` DIRECTORY SCAN (it runs after the menu) that REGISTERS a folder; it does not mean the mod is on.

**Method lesson, the important one: prove the thing under test is actually running BEFORE asking why it does not work.** All eight "verification failures" were run against a mod that was not loaded — I autopsied an experiment that had never happened.

### ⚠⚠ The `.dat` CAN express per-civ unit availability — the "cannot" was too strong

`_probe/test_dat_grant_route.py` (A–E PASS): **effect command type 2 with `b=1`** (`a` = unit) on a tech whose **`civ` field names the civilization** is a per-civ unit enable, and shipped data uses it:

```
tech 1363  civ 57 Muisca      'Guecha Warrior (make avail)'    type 2 a=2562 b=1
tech 1471  civ 61 Varangians  'Jarl (make avail)'              type 2 a=2708 b=1
tech 1481  civ 62 Danes       'Jomsviking (make avail)'        type 2 a=2711 b=1

**And they need no tree row:** of 112 civ-owned techs carrying a type-2 command, **99 are ABSENT** from the owning civilization's tree — they apply because of `tech.civ` alone, exactly like a civilization bonus. (The other 13 are `ResearchedCompleted`, e.g. tech 624 Malay.) So a `.dat`-only grant is **not circular** — it does not depend on the tree layer that has failed to take effect.

### ⚠⚠⚠ Only ONE of three `.dat` edit routes is safe — measure the output, don't assume

Pinned by `_probe/test_dat_edit_routes.py` (all PASS), which tries all three against a real edit:

| route | result |
|---|---|
| **1. add a command to an EXISTING effect** (in-place length change) | **delta +3,061,463 bytes**, 34,740 model-vs-raw mismatches, re-parse dies `struct.error: bad char in struct format`. `write_effect` writes `len(commands)` records with no notion of the original byte span, so everything after it shifts and the verbatim replay desynchronises. **UNSAFE.** |
| **2. append a new TECH** | serialises and re-parses, **but** `write_tech`'s `_new` branch hardcodes the three `ResearchResourceCost` slots as zero (`aoe2mod/dat/writer.py:739`) while every shipped `make avail` tech has `costs[].type == -1` (901 of 1510 techs use `(-1,-1,-1)`). The model dict **cannot** override it. |
| **3. append a new EFFECT and repoint an EXISTING civ-owned tech's `effect_id`** | **delta +38, exactly 2 mismatches** (the effect count and that one i16), clean re-parse. **CHOSEN.** It also leaves the shipped tech's bytes untouched, so no scaffolding is synthesised. |

**The strongest subject for a per-civ grant**: `tech 263 'Longbow (make avail)'`, `civ == 1` (British), effect 251 = `[(type 2, a=8, b=1)]` — unit 8's `EnablingResearch` is 263 and the British are the only civ that can build Longbowmen, so it is a per-civ unit gate the engine demonstrably honours. Editing it gives a **built-in second control**: if the Longbowman disappears, the edit itself broke something and the result is unreadable; if it survives and the new unit does not appear, type 2 does not grant units added this way. **Check WHERE that unit is trained before pointing a human at it**: `British unit 8 Longbowman train_locations = [{'unit_id': 82}]`, and `building 82 = Castle, Age ID 3` — a Dark-Age Archery Range could never show it (I wrote that wrong once and wasted a test).

```

and the product's `unit.stat` for 「村民 生命值 =1000」 compiles to **1,701 edits = 27 × 63 civs**. Editing only id 83 produces the worst possible symptom: **the unit reads 1000 while standing still and reverts to 25 the moment it is given a task.** When hand-rolling an experiment, assert `changed_ids == set(family)` against the artifact — that is what `_probe/build_smoke9.py` does.

**And when a pin names an artifact, do not hard-code which experiment is installed.** Two pins failed purely because their literal folder name (`aoe2mod Smoke6 …`) was replaced by a later smoke; they now *discover* the folder and assert on the built artifact (the measurement is about content, not today's presence). Likewise `deep == third_party_deep + len(deep_names) - len(third_party)` is a tautology — assert against the measured sets instead.

### ★★★★★ GIVING A CIVILIZATION A UNIT IT CANNOT BUILD — the working recipe (verified in game)

**Proven end to end on 2026-10-16.** `dsh test v7` passed all three in-game controls in one session: the villager stayed at 1000 hp after being given a task, the Castle-Age Longbowman was unaffected, and **the Dark-Age Barracks showed the Champi Scout button** (`ABC都没问题了`). Four layers, every one necessary — and **one field that must be left alone**:

| # | layer | edit |
|---|---|---|
| 1 | `.dat` effect | append a new effect whose commands are **the anchor technology's own commands** plus `(type 2, a=<unit id>, b=1)` |
| 2 | `.dat` tech | re-point a tech **the target civ already owns and that fires at 0:00** at that effect (`effect_id`) — **append an EFFECT, never a TECH**: `write_tech`'s `_new` branch hard-codes the three `ResearchResourceCost` slots to 0 while shipped records use `-1` |
| 3 | `.dat` **button slot** | move the unit's `train_location.button_id` to a slot the target civ has FREE (an in-place 1-byte patch; **re-derive the offset on the serialized stream**, appending an effect moves it) |
| 4 | JSON | add the `CivTechTrees/<CIV>.json` row **and** the `futuravailableunits.json` entry (copy both verbatim from a civ that has the unit) |

**Layer 2 carried the whole bug.** The anchor must be chosen by **`Research.RequiredTechs`**, not by the tech's name: `tech 383 'C-Bonus, +25% Shepherd'` has `RequiredTechs == []` (fires at 0:00), while `tech 263 'Longbow (make avail)'` — the one whose *name* says "make avail" — has `[102, 266 'Castle built']`. v5/v6 used 263, so the button only appeared after a Castle was built (`_probe/probe_anchor_why.py`; the product rule lives in `datgrant.pick_tech`).

**★ Do NOT write `TechTree.UnitConnection.EnablingResearch`.** Three measurements (`_probe/probe_enabling_scope.py`): (1) the confirmed recipe wrote no such byte — its script patches only when the shipped value is not `-1`, and unit 2550 ships as `-1`; (2) the field does not gate — v5 set it to 263 and v6 cleared it to `-1`, and both behaved identically in game, so the Castle gate came from the *effect's anchor*, not this field; (3) it is **one connection per unit id, not per civilization**, so writing British's private tech 383 onto unit 2550 — which Incas/Mapuche/Muisca/Tupi build and the British do not — claims to all 63 civs that a British technology enables it, and the shipped corpus contains **zero** precedents for that foreign pairing. The field is still read and reported; it is simply never overwritten. **Copying a hand-built experiment's field list is not enough — ask which of its writes the game actually needed.**

**Layer 4 is the one that took 69 rounds to find, and it is not in the data model — it is a UI collision.** `button_id` groups units into button CHAINS (one slot cycles through an upgrade line). Measured, counting only units the civ's tree actually grants:

| slot | British | Incas |
|---|---|---|
| button 1 | **5 available** — 74 75 77 473 567 (militia line) | **4** — 2550 2588 2552 2554 (whole champi line) |
| button 2 | 3 available (spear line) | 3 |
| button 3 | **0 (free)** | 0 |
| button 4 | **0 (free)** | 0 |

The Incas put the Champi Scout in button 1 because their militia line is `NotAvailable` and the slot is free. The British already have five available units there, so the same `button_id` **masks** the new unit. Moving it to the free button 4 made it appear — a **one-byte change**. Button 4 is also the semantically right home: it holds `Eagle 751-753`, `Huskarl 759/761`, `Flemish Militia 1699`, `Hoplite 2110/2111`, `Phalangite 2384/2385`, `Temple Guard 2586/2587`, `Varangian Guard 2703/2704` — regional and unique units, and the Champi Scout's `Node Type` is `RegionalUnit`.

Corpus check: only **12** (civ, building, slot) cases mix two different `unitlines.json` line ids, and all 12 are **one line reachable at two buildings** (`Huskarl 41@Castle` / `759@Barracks`), not two unrelated chains. `unitlines.json` alone cannot decide button sharing — read the units' own `task_swap_group` too (only 3 non-zero groups / 32 units exist; `0` means NO group, so treating `{0}` as "one group" is a tautology — a first draft of the probe did exactly that and lied).

**Known side effect:** the age at which the unit appears follows the tech that `EnablingResearch` points at, NOT the tree row's `Age ID`. Pointing at `tech 263` (the Longbowman's, a Castle-Age unit) made the Champi Scout appear only after a Castle was built, even though its copied tree row says `Age ID = 1`.
